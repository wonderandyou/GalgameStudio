# 千节点怎么分批写，才不会崩

这份文件解决一个具体问题：**一部 2 小时的作品接近 1000 个节点，
任何一次「把整部写完」的尝试都会失败。**

失败不是因为模型笨，是因为三件物理事实：

| 事实 | 后果 |
|---|---|
| 单次输出有长度上限 | 写到第 300 个节点就断在半句话上，后面的全丢 |
| 上下文会越滚越长 | 读得越多越慢越贵，到后面反而写得最差 |
| 一次写太多，错误会累积 | 第 20 个节点剧情跑偏，剩下 800 个全跟着偏，回头只能重写 |

所以规矩不是「尽量少写」，是**每次只写一点点，但每次都落盘、都校验**。

---

## 一、写入粒度

| 层 | 单位 | 一次处理多少 | 落盘时机 |
|---|---|---|---|
| 章 | 12~16 个节点 | 一章分 1~2 次写完 | 每批 `write_nodes` 立刻落盘 |
| 批 | 8~15 个节点 | **这是你的操作单位** | 每批结束立刻 `validate_graph` |
| 节点 | 1~6 句台词 | 一次写完一个节点的全部台词 | 随批落盘 |

**一批 = 一个完整的戏剧单元。** 不是凑够 10 个节点就停，
而是「这一段戏说完了」才停。通常是：

- 一次对话交锋（3~5 节点）
- 一个场景的起承（6~10 节点）
- 一次选择前后（choice + 两条支线各 2~3 节点）

---

## 二、每次开工能看到什么

你**看不到全书**，只能看到这些。所以别指望「先在脑子里想好整部书」：

| 能看到 | 怎么看 |
|---|---|
| 需求与目标时长 | `project_brief` |
| 幕/章骨架 | `get_structure` |
| 本章已写节点（ref + 台词前 20 字） | `get_chapter` |
| 前面各章的摘要 | `get_chapter` 里带的 `prev_summary` |
| 角色表 | `list_characters` |
| 全书校验结果 | `validate_graph` |

**看不到**：其他章的完整台词。这是刻意的 —— 靠摘要传递上下文，
否则写到第 60 章时上下文会爆。

这意味着一个硬要求：**摘要必须写得够用**。写摘要时假设
「读的人只看这一段，要接着往下写」，把该交代的都交代了。

---

## 三、正确的循环（一章）

```
get_chapter(c03)
  ├─ 已知：本章梗概、已有 s01~s05、前情摘要
  │
  ├─ write_nodes(c03, [s06..s13])      ← 8 个
  ├─ validate_graph(chapter=c03)        ← 有错立刻改
  ├─ write_nodes(c03, [s14..s18])      ← 收尾 + 一个 choice
  ├─ 连边：connect_nodes 或 choices
  ├─ validate_graph(chapter=c03)        ← 再校一次
  └─ finish_chapter(c03, summary)       ← 写摘要，标记 done
```

一章超过 20 个节点就分两轮，**不要硬塞进一次**。

---

## 四、断点续跑

任何时候中断（超时、报错、被叫停）都不会丢已写入的内容 ——
每批 `write_nodes` 都立刻存盘。

恢复时**不要从头再来**，照这个顺序接：

1. `get_structure` —— 看哪些章 done
2. `list_chapters(status=writing)` —— 找写到一半的章
3. `get_chapter` —— 看它停在哪个 ref
4. 从下一个 ref 接着写

**从第一章重写是严重错误**，会把已经写好的内容覆盖掉。

---

## 五、写偏了怎么救

发现剧情跑偏（人物不像、节奏塌了、伏笔丢了），按损失大小处理：

| 损失范围 | 处理 |
|---|---|
| 本批还没 `finish_chapter` | 继续在本章内调整，靠后面的节点圆回来 |
| 本章已 `finish_chapter` | 下一章开头用 1~2 个节点自然找补，不要回头删 |
| 已经跨了 3 章以上 | 在 `finish_chapter` 摘要里明确记下偏差，让后续章节按新的走向走 |

**不要为了修前面而整章删除重写**，除非用户明确要求。
读者感知不到「计划里本来不是这样」，只感知得到「读起来断不断」。

---

## 六、失败重试

| 情况 | 做法 |
|---|---|
| `write_nodes` 返回 ref 冲突 | 换新 ref（查 `get_chapter` 已用的），不要改已有的 |
| `validate_graph` 报孤儿节点 | 用 `get_chapter` 找到孤岛入口。插入原路线前先接好段尾，分支则保留已有选项和目标 |
| 报 choice 缺出口 | 给这个 choice 补第 2 个选项 |
| 报 to 指向不存在的 ref | 用实际存在的 ref 替换，或补一个目标节点 |
| 再次遇到同类错误 | 刷新 `get_chapter`，按最新的边和校验结果修已有 ref |

---

## 七、进度自检（每写完 5 章做一次）

| 检查 | 期望 |
|---|---|
| 已完成章数 ÷ 总章数 | 与已用时间大致成比例，落后就要加快节奏 |
| 实际节点数 ÷ 目标节点数 | 在 0.85~1.15 之间 |
| 平均每章节点数 | 12~16，低于 8 说明一章写太薄 |
| choice 节点占比 | 8%~15%，太少没得选，太多像迷宫 |
| 每 5 章是否有一次「不可逆变化」 | 没有就要设计一个 |

**节点数不够是最常见的问题。** 一部要求 60 分钟的作品只写了 200 个节点，
玩起来就是 20 分钟的量。宁可多写场景过渡和反应镜头，也不要草草推进主线。
