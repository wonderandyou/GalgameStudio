# 分支与结局

分支是 Galgame 和「有插图的电子小说」唯一的区别。大部分业余作品的分支是假的 ——
选项点下去，走三段不同的台词，然后合回同一条线，玩家第二次玩就发现了。

这份文件定义什么叫真分支。

---

## 一、真分支的判定

一条分支算「真」，必须满足**至少两条**：

1. **后面有超过 20 个节点走的是不同内容**（不是换个说法）
2. **改变一个角色的状态**（好感、信任、某个秘密谁知道）
3. **改变可获得的信息**（A 路线玩家不知道的事，B 路线玩家知道）
4. **改变可达的结局**

只满足 0~1 条的，是**假分支**，写着累、玩着空，不如不写。

---

## 二、结构：网，不是树

新手常犯的错是画一棵完美的树 —— 3 层每层 2 选 1 就是 8 条线，
每条线都要完整写一遍，篇幅爆炸，写到一半放弃。

正确做法是**网**：

```
         ┌── A 线（5 章）──┐
起点 ── 选择                 ├── 汇合点（2 章）── 最终选择 ── 结局
         └── B 线（5 章）──┘
```

- 分支**分开走一段**（5~10 章），然后**汇合**
- 汇合后玩家带着不同的「状态」继续（谁受伤了、知道什么、和谁关系如何）
- 汇合点之后的台词要**能容纳两种状态**，或者用条件选项区分

这样一个 60 章的作品，只需要写 60 章 + 两条 8 章的支线 ≈ 76 章，
而不是指数爆炸。

### 分支的宽与深

| 参数 | 建议 | 说明 |
|---|---|---|
| 分支深度（嵌套几次选择） | 2~3 | 超过 3 层，玩家会迷路 |
| 并行支线条数 | 每幕 ≤ 2 条 | 同时存在的线多了写不动 |
| 支线章节数 | 5~10 章 | 少于 3 章的分支没意义 |
| choice 节点占比 | 全书 8%~15% | 1000 个节点里 80~150 个 choice |

## 二·B、落地：分支在节点里长什么样

上面那棵树不是示意图，要真的写成节点。`write_nodes` 里一个 choice 节点长这样：

```json
{"ref": "c01-s11", "type": "choice", "title": "票在两个人中间",
 "lines": ["她把湿透的额发别到耳后"],
 "choices": [
   {"label": "「那就两个人一起走」", "to": "c01-s12"},
   {"label": "「你把它撕了」",       "to": "c01-s13"}
 ]}
```

三条硬规则，违反任何一条都会被 `validate_graph` 打回：

1. **2~4 条 `choices`，每条 `to` 指向不同的 ref。**
   两条选项指同一个节点 = 玩家选了两次结果一样，这就是假分支。
   写入时会被直接拒（`DUPLICATE_CHOICE_TARGET`）。
2. **两条腿必须先各走一个自己的节点，才能汇合。**
   - ✗ 错：两个选项都指向 `c01-s12`（当场合并）
   - ✓ 对：`c01-s12` 和 `c01-s13` 是两个不同的 scene，各写各自的内容；
     它们**各自的下一节点**（可以是同一个 `c01-s14`）才是汇合点
3. **汇合点要新建，不要复用前面的旧节点。**
   复用旧节点九成会成环，`write_nodes` 会报 `GRAPH_CYCLE`。

### 一个分叉吃几个节点

```
分叉节点(1) + A 腿(至少 1) + B 腿(至少 1) + 汇合点(1) = 至少 4 个
```

**写 choice 之前先看还剩多少预算。** `write_nodes` 返回值里的
`remaining_budget` 就是真实还能新建几个（已经算上 2 个弹性位）。
预算不够时，宁可这一轮不写分叉，也别把两条选项塞进同一个节点。

### 分批写的时候

分支经常跨两个批次：

- **第一批**：写 choice 节点 + A 腿。B 腿那个 ref 还没写，就先填上去挂着
- **第二批**：把 B 腿和汇合点写出来，系统自动把挂着的 ref 解析掉

`get_chapter` 返回的 `nodes[].choices` 里如果还是 `to_ref` 而不是 `to`，
说明那条腿还没落地 —— 补齐了才能 `finish_chapter`。

## 二·C、两类分支：必要的和不要紧的

分支不是只有一种。分清楚这两类，作品才既有多结局又读着不空：

| `branch_kind` | 叫什么 | 作用 | 数量谁定 |
|---|---|---|---|
| `key` | **必要分支** | 选项直接决定走向哪个结局。选错就走不到真结局 | **全书 1~10 个**，由玩家设定；每章该写几个任务里会告诉你 |
| `flavor` | **非必要分支** | 对话不同、氛围不同，两条腿各走一小段**汇合回主线**，不影响结局 | **全书可以几十上百个**，同样摊到各章 |

必要分支多一个，就多一个结局要收尾；气氛分支多一个，只是多一小段对话。
所以：**必要分支要抠着写，气氛分支能铺就铺**。

### 为什么要专用 `flavor`

玩家的「我在做选择」的手感，主要来自非必要分支 —— 而且它便宜：拆一小段对话、两三条腿再合回来，
不增加结局数量，也不让篇幅爆炸。**全是必要分支的作品读起来很累**：每个选项都事关结局，
玩家压力大、作者也写不完。

`flavor` 的正确形态：

```
         ┌── 她在等你说话（2 节点）──┐
五点 ──── 选择                      ├── 两个人一起下去（主线继续）
         └── 你先开口（2 节点）    ──┘
```

两条腿**内容真的不一样**（不是换说法），但**最后指向同一个节点**。

### 写错的两种典型

| 错法 | 表现 | 系统怎么拦 |
|---|---|---|
| 该 key 的标成 flavor | 不同选项最后进了不同结局 | `FLAVOR_AFFECTS_ENDING` |
| 该 flavor 的标成 key | 每章五六个分支，玩家每个都紧张 | 不拦，但作品会变得难读 |

**默认 `key`**。写 `flavor` 时问自己一句：这段结束之后，两条路的人看到的是同一个场景吗？
不是同一个，就别标 `flavor`。

```json
{"ref": "c01-s06", "type": "choice", "branch_kind": "flavor",
 "title": "谁先说",
 "lines": ["两个人都没说话"],
 "choices": [
   {"label": "「你等了多久」", "to": "c01-s07"},
   {"label": "什么都不说", "to": "c01-s08"}
 ]}
```

## 二·D、必要分支的形态：**早分、长跑、不回头**

`key` 和 `flavor` 的结构完全不一样，别拿同一套画法套。

`flavor` 是短分叉（上面那张图）；`key` 是**在故事早期劈开主线，然后各跑到底**：

```
第一幕末（全书 10%~25% 的位置）
      ├── A 链 ──── 8~12 章 ──── 结局：真
      └── B 链 ──── 8~12 章 ──── 结局：坏
```

三条硬要求：

1. **位置要早**：`key` 分支落在**全书前 25%** 的章节里。
   第 20 章才分叉，玩家已经读完三分之二，再分也没有「我的人生从这一刻改道」的重量。
2. **不汇合**：`key` 的两条腿**不要合回主线**。它们各自是主线的另一种可能，
   一直走到各自的结局。合回来 = 玩家发现「选了等于没选」。
   （只有 `flavor` 才要求「先各走一个节点、然后汇合」。）
3. **各走各的**：分开之后，两条链的 `bg_key`、在场角色、角色状态、玩家知道的信息
   都该不一样。两条链只是台词换个说法，那本来就该标 `flavor`。

### 并行链怎么写才不散

- **每一链自己的地点**：A 链在她家，B 链在车站 —— 不要两条链都在同一个天台。
- **每一链自己的状态**：她走了 / 她留下 / 谁都没走，之后所有人对「你」的态度都不同。
- **结局收在链尾**：一条链走到 `end_kind`，不要中途跳去别的链的节点。
- **`key` 不要嵌套 `key`**：每多套一层就多指数级的结局要收尾。
  真要三段式，用「前半段同一条主线 → 中期再分」，不要在一层里套两层。

`flavor` 的嵌套层数才受「分支嵌套」限制；`key` 分支按上面这种并行写法，
并行几条都不会被深度校验拦。


### 好的选项

- **两个都有代价**，玩家真的犹豫
- 选项文字**暗示不透露**（不能说破后果）
- 差距是**价值观**的差距，不是「好/坏」

```
✓ 「把票给她」        /  「把票撕了」
✓ 「说实话」          /  「什么都不说」
✗ 「善良地帮她」      /  「邪恶地拒绝她」    ← 玩家一眼看穿
✗ 「继续」            /  「不继续」          ← 没有信息量
```

### 禁止的选项

| 类型 | 问题 |
|---|---|
| 「是」/「否」 | 无信息量，闭眼也能选 |
| 「去天台」/「去车站」 | 地点选择，除非后面真的走向不同 |
| 一个明显正确一个明显错误 | 没有张力，玩家在考道德题 |
| 3 个以上选项且都不影响后续 | 装饰性选择，删掉 |

2 个选项是标准；4 个只在关键节点用，而且每个必须能走向不同结局。

## 四、结局

一部 60 分钟的作品，**3~5 个结局**是合适的。少于 3 个，分支没意义；
多于 6 个，每个都写不深。

| 类型 | 数量 | 特征 |
|---|---|---|
| `true` 真结局 | 1 个 | 需要特定选择组合，最难达成，信息量最大 |
| `good` 好结局 | 1 个 | 两全的走法，玩家第一次通关通常到这里 |
| `bad` 坏结局 | 1~2 个 | 不是「死掉」，是某种关系的不可挽回 |
| `alt` 分歧结局 | 1~2 个 | 另一种合理的生活，谈不上好坏 |

**好结局和真结局差在哪**：好结局是「事情办成了」，真结局是「事情办成了，而且玩家知道了别人不知道的那层」。
好结局可以只靠一两个关键选择就够；真结局要串起整部的伏笔。别把两者写成一个，也别把好结局写成坏结局的安慰版。

### 硬性

- **不许只有真结局一个收尾**。至少 3 个可达结局
- `end_kind` 必须填，不能留空
- 每个结局的节点要有 1~3 句「停得住」的收尾台词，
  不要用「故事到此结束」「感谢游玩」这种话
- 坏结局不是惩罚玩家，是展示另一种真实

### 达成条件要可推

玩家读真结局时，应该能回想起来「我做了哪个选择才走到这里」。
如果达成条件纯随机或纯靠运气，那不叫真结局，叫抽奖。

## 五、状态传递

分支真正的价值在**汇合之后**。汇合点用条件选项表达状态：

```
choice 节点：
  - label: "「你手怎么了」"   condition: "flag:injury == true"
  - label: "「走吧」"          condition: "flag:injury != true"
```

条件表达式目前支持两种形式：

| 形式 | 例子 |
|---|---|
| 标记 | `flag:secret_known == true` |
| 计数 | `trust_heroine >= 3` |

**不要滥用**。条件选项只在真的需要区分的地方用，
滥用会让作者自己也记不清哪条线是什么状态。

## 六、写歪了怎么修

### 接回孤儿节点

`ORPHAN_NODE` 表示从本章入口走不到该节点。一段连续的场景可能一起报错，
先用 `get_chapter` 查看 `orphans` 和 `edges`，找到那段剧情的入口。

1. **插入现有路线**。若要把一段剧情插进 A → B，先把该段的末尾接到 B，
   再用 `connect_nodes(from=A, to=该段入口, replace=true)` 改 A 的出口。
   如果换边会切断原本可达的场景，工具会返回 `WOULD_ORPHAN`，图保持原样。
2. **增加一条分支**。用 `write_nodes` 编辑分叉节点的 `choices`。保留原目标，
   并让另一条选项指向脱离的路线入口。
3. **保留下一章的接点**。非最后一章要留一个接点。若所有路线都以 ending 结束，
   选出剧情应继续的那条，用已有 ref 把合适的结尾改为 scene，省略 end_kind，
   并将该场景的出口留给下一章。

## 七、分支自检清单

写完一个 choice 节点，问四句：

- [ ] 两个选项，玩家会真的犹豫吗？
- [ ] 选完之后，**至少 20 个节点**内容不同吗？
- [ ] 会改变结局可达性，或改变角色状态吗？
- [ ] 汇合的地方，两种状态都说得通吗？

四个里有两个答不上来，这个 choice 就是假的，删掉改成普通节点。
