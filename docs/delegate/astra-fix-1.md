## 先明确：`node_count` 和 `target_minutes` 谁说了算

（上一版需求这块我写矛盾了，**以这一节为准**）

**以 `node_count` 为准。**

理由：

- `app/agents/loop.py:58` 是 `self.total = pipeline.params['node_count']`，生成量直接由它决定
- 收尾有 `WRITER_COUNT_MISMATCH` 硬校验，节点数对不上直接报错
- `target_minutes` 目前没有参与生成量控制，只被记进 `agent_state`

所以 **时长是从节点数派生出来的量**，不是输入：

```
节点数 = 时长 × 8.125       时长 = 节点数 ÷ 8.125
488 节点 → 60 分钟          1000 节点 → 123 分钟
```

要落地的三条：

1. 前端拖时长滑条时同时改节点数（**已做**，`ui/app.js` 两个滑条双向联动）
2. 后端只收到 `target_minutes`、没收到 `node_count` 时，按 `round(target_minutes × 8.125)` 推算
3. 两个都收到且互相矛盾时，**以 `node_count` 为准**，记一条 warn 日志（不要报错 —— 用户可能手动改过其中一个）

对应地，验收里我按**每节点字数**判断，不按总字数，这样跟时长解耦。

## 问题 1（最重要）：一千个节点只有 2 个分支

**实测**：`node_count=1000, branch_depth=2` 生成出来是这样：

```
类型: {start: 1, scene: 994, choice: 2, ending: 3}
```

994 个场景节点，只有 **2 个选择节点**。玩起来就是一条直线，只有一个地方能选。

**根因**在 `app/agents/loop.py:284` 和 `:290`：

```python
depth = min(self.pipeline.params.get('branch_depth', 2), (self.total - 2) // 2)
...
for info in chapters:
    branches = min(depth, (info['node_budget'] - 1) // 2)
    depth -= branches          # ← 这里把「预算」用掉了
```

`depth` 是个**总预算**，从 `branch_depth`（默认 2）开始，每分配一章就扣掉。
所以全书总共只能产生 `branch_depth` 个分叉点，跟节点数、章数完全无关。

**语义错了**：`branch_depth` 应该表示「分支嵌套几层」（一个 choice 的两个走向各自再分叉几次），
而不是「全书只能有几个 choice」。

**应当的行为**：一部完整的 Galgame，选择节点应该占全书节点的 **8%~15%**。
1000 节点 → 80~150 个 choice 节点。

参考分布（skill 里写死的标准，`app/skills/writer/03-branch.md`）：

| 参数 | 建议 |
|---|---|
| choice 节点占全书比例 | 8%~15% |
| 单个 choice 的出口数 | 2~4 |
| 并行支线条数 | 每幕 ≤ 2 |
| 分支嵌套深度 | 2~3 层 |

**修法建议**（自己判断更好的方案）：

- `branch_depth` 改成控制「嵌套深度」，不影响总数
- 分叉点按**章**分配：每章 1~2 个 choice，而不是全书共用 2 个预算
- 保证最终 choice 占比在 8%~15%，写进循环的收尾校验（跟现有的
  `WRITER_COUNT_MISMATCH` 一样，达不到就报错，别静默过去）

## 问题 2：mock 文本撑不到目标时长

**实测**：`node_count=1000` 生成出来

```
台词: 1000 句 / 8998 字，平均每句 9 个字
```

按「每节点约 36 字」的标准，1000 节点应该是 **36000 字**，实际只有四分之一。

**根因**在 `app/agents/loop.py:227-229`：

```python
node = dict(ref=ref, type='scene', title=f'片段 {index + 1}', who=who,
            lines=['她听见雨声停在窗边'], bg_key='mock_rain', ...)
```

每一句都是同一句、9 个字。1000 个节点就是同一句话重复 1000 遍。

**这不是「模拟模式无所谓」** —— 因为：
1. 没有 LLM key 的用户，看到的就是这个
2. 它没法验证「节点数对不对、时长够不够」这个核心指标

**应当的行为**（按 `app/skills/writer/SKILL.md` 里定的预算公式）：

```
每个节点 1~3 句台词，每句 8~40 字，平均约 32 字
节点平均字数 ≈ 1.5 句 × 32 字 ≈ 48 字
```

1000 节点 ≈ 48000 字。但你按目标时长倒推的节点数是 `T × 8.125`，
所以 **每节点应该约 36 字**（1000 节点对应 120 分钟）。

**默认 60 分钟 = 488 节点 = 约 18000 字。**

修法：

- mock 台词要有**变化**（准备一组占位句子池，按章节/序号取，不要全书同一句）
- 每节点 2~3 句，总字数达到「目标分钟数 × 300」的 ±20% 以内
- 收尾时把实际字数写进 job 的 stats，方便核对

## 问题 3：原子写文件在 Windows 上会失败

**实测报错**：

```
PermissionError: [WinError 5] 拒绝访问。:
  '...j_671c....json.u3f_4xib.tmp' -> '...j_671c....json'
```

发生在写了 721/1000 节点时，整个任务失败。

**根因**在 `app/store.py:22`：

```python
temp.replace(path)
```

`Path.replace` 在 Windows 上就是 `os.replace`。只要目标文件**此刻正被任何进程打开着**
（哪怕只是读），就抛 `WinError 5`。

**触发条件**：有外部工具（监控脚本、日志查看器、备份程序）在读 `.jobs/*.json`。
前端用 SSE 不读文件，所以正常使用不会撞，但这是颗定时炸弹。

**修法**：包一层重试，Windows 上这是标准做法。

```python
for attempt in range(5):
    try:
        temp.replace(path)
        return
    except PermissionError:
        if attempt == 4:
            raise
        time.sleep(0.02 * (attempt + 1))
```

（注意别吞掉其它异常类型，只重试 `PermissionError`。）
