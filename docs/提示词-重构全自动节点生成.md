### 语义要点（别搞错）

| 字段 | 语义 |
|---|---|
| `start` | 有且只有一个，id 必须是 `n1` |
| `ending` | `end_kind` 必须有值，**且 `choices` 必须为空**（结局没有出口） |
| `choice` | **必须有 2~4 个 `choices`**，`branch_kind` 必须是 `key` 或 `flavor` |
| `scene` | 普通叙事，推进靠 `choices` 里一个「唯一出口」（结构上也是 choices，只有 1 个） |
| `branch_kind=key` | 必要分支，决定走向哪个结局 |
| `branch_kind=flavor` | 气氛分支，只改对白氛围，**必须汇合回主线** |
| `chars[].pose` | 是**图片路径**，不是姿态名。姿态在 `chars[].stance` |
| 资产路径 | 一律 `assets/...` 的 POSIX 相对路径，禁止盘符/反斜杠/`..` |

## 3. 世界规则（`app/engine/graph.py::validate_graph` 会逐条检查）

生成结果必须满足全部条件，否则整轮判死：

1. 节点 id 不重复
2. 有唯一 `start`（n1）和**至少一个** `ending`
3. `edges` 与各节点的 `choices` 完全一致（`edges` 由 `edges_from_nodes()` 从 choices 展开，别手动维护）
4. 边 id 不重复
5. 所有资产路径的文件真实存在
6. 语音文件能读出时长，且与字数偏差不超 60%
7. `ending` 必须有 `end_kind` 且无 `choices`
8. `choice` 必须有 2–4 个 `choices`
9. **`start` / `scene` 必须有一个后继** ← 断头节点就是违反这条
10. `choices` 不能指向不存在的节点
11. 每句台词都要有 `voice`
12. **图中不能有环**
13. **不能有不可达/孤立节点**（所有节点必须从 n1 可达）

## 4. 现在的实现，以及它为什么必然产生断头节点

文件 `app/agents/loop.py` 里的 `WriterLoop.run()`：

```
plan()            → 把总节点数切成 N 章（每章 node_budget，默认 ~16）
for chapter in chapters:
    model_chapter()  # 让模型调 write_nodes 写这一章的节点，自己连边
    chapter_branch_error()  # 校验
connect_nodes(...)  # 下一章开头，从「上一章的开放出口」接到本章第一个节点
```

**致命缺陷**（这是主人实测到的问题，必须解决）：

`chapter_branch_error()`（`loop.py:408`）只检查三件事：
- 必要分支数量够不够
- 分支层数 ≤ depth
- 最后一章有没有真结局

**它不检查「本章有没有留下没有出边的节点」。**

于是：模型写气氛分支时，分叉出去的两条线经常没汇合，留下 2~3 个悬空 scene；
校验通过；下一章只从**一个**「开放出口」往后接；剩下的悬空节点就**永远断头**了。

实测数据：项目「了」510 个节点里有 **57 个断头节点**（c02~c29 都有，c12 最多 4 个）。

### 4.1 归因实测（这不是猜的，是跑出来的）

`_qa/_deadend_analysis.py` 对项目「了」的统计结果：

```
断头节点：57 个
断头节点的直接前驱类型：{'choice': 54, 'scene': 3}
断头节点到最近分叉点的步数：[1, 1, 1, ...(54 个 1)... , 2, 2, 7]
其中「分叉后 1~3 步就断」的占比：56 / 57

全书分支构成：key（必要）分支 4 个，flavor（气氛）分支 50 个
有断头的章：28 / 31
```

读法非常直接：

- **50 个气氛分支，长出一个节点就断了，没有一个汇合回主线**
- **54 个断头的直接前驱就是 choice 节点**，而且**断在分叉后第 1 步**
- 覆盖 28/31 章，不是个别情节写漏，是**流程本身必然产出这个结果**

所以「补边」只能一处一处打补丁（补完这 57 个，下次生成又长 57 个新的）。
必须从生成方式上根治。

播放器现在只能「走到死路就退回上一个选择」兜着 —— 这是绕过，不是修好。

## 5. 目标架构：一次成树 → 冻结 → 填充

### 5.1 为什么不能真的「一次调用生成 510 个节点」

LLM 单次输出长度有限。1000 个完整节点（含台词）写不进去。

**但结构可以。** 所以拆成两阶段：

```
阶段 A：骨架（Skeleton）  ← 只生成「拓扑」，不写台词
        一次（或按幕分批）产出整棵树的节点表：id / type / 出边 / 分支标签 / 结局类型
        产出后在内存里合并成一整张图，**全校验**，不合格重生成
阶段 B：填充（Fill）      ← 只往已有节点里写台词
        按骨架顺序分段填，**不许新增节点、不许增删边**
```

关键：**拓扑在阶段 A 就定死并锁定**，阶段 B 物理上无法造成断头。

> **关于「分批」的边界，别理解错**：
> 如果一次输出装不下整棵树，可以按幕分多次调模型 —— 但这只是**省输出长度的工程手段**，
> 不是结构上的分段。每一批拿到后只在内存里追加，**全部合并完才做一次全校验**，
> 校验通过才落盘成 graph。绝不允许「每批各写一段 graph、各自校验、各自落盘」——
> 那正是现在断头的来源。

### 5.2 骨架的数据结构（新文件 `app/engine/skeleton.py`）

```python
@dataclass
class SkeletonNode:
    ref: str                      # 骨架内临时 id，如 'k007'
    type: str                     # 'start' | 'scene' | 'choice' | 'ending'
    title: str                    # 8 字以内
    act: int                      # 第几幕（1 起）
    chapter: str                  # 'c01'
    to: list[str]                 # 出边的 ref 列表
    labels: list[str] = None      # choice 的选项文案（与 to 等长）
    branch_kind: str = None       # key / flavor（只有 choice 有）
    end_kind: str = None          # true / good / bad / alt（只有 ending 有）
    summary: str = ''             # 这一节点发生什么，20~40 字，给填充阶段当 brief
```

```python
@dataclass
class Skeleton:
    nodes: list[SkeletonNode]
    logline: str                  # 一句话故事
    acts: list[dict]              # [{'id':'a1','title':'第一幕','chapters':['c01','c02']}]
    meta: dict                    # 目标节点数 / 分支深度 / 结局数等

    def to_graph_stub(self, characters, project) -> dict:
        """转成 graph 雏形：节点齐全、边齐全、台词是占位。可直接被 validate_graph 校验结构。"""
```

### 5.3 骨架校验（`validate_skeleton`，必须实现）

只查结构，不查资产/语音，**任何一条不过就重生成骨架**：

1. 有且只有 1 个 start，且是列表第一个
2. 至少 1 个 ending；`true` 结局至少 1 个
3. 除 ending 外**每个节点 `to` 非空** ← 消灭断头
4. 所有 `to` 指向存在的 ref
5. `choice` 的 `to` 长度 2~4，`labels` 与 `to` 等长
6. `scene` / `start` 的 `to` 长度**恰好 1**
7. `ending` 的 `to` 长度为 0
8. 从 start 出发能到达全部节点（不可达 = 错）
9. 无环
10. `branch_kind=flavor` 的分支**必须能汇合**：从它每条子路径出发，都能到达同一个节点（汇合点）
11. 分支同时开启层数 ≤ `depth`（默认 2~3）
12. 节点总数落在 `[目标 * 0.9, 目标 * 1.1]`
13. `act` 只是**可选的分组元数据**（用于进度显示和统计），全部填 1 也合法。
    **不要再引入「章」这个生成单位** —— 骨架是一张完整的网，不按章切。

### 5.4 骨架生成（新文件 `app/agents/outline.py`）

```python
async def generate_skeleton(pipeline, tools, *, target_nodes, depth, endings, requirement) -> Skeleton
```

做法（两条路径，都必须实现）：

- **真模型路径**：给模型一份「骨架 JSON schema + 硬规则」，让它按幕分批输出，每批产出若干节点的骨架条目。
  批量边界必须咬合：上一批的**最后一批出口**作为下一批的**入口**传入。
  每批产出后**只在内存里追加**，全部拿到后再合并校验 —— 不落盘、不写 graph。
  **校验失败就把失败原因原样回喂给模型重生成**（最多 3 次），仍失败则抛 `ProviderError('SKELETON_INVALID', ...)`。
- **兜底路径（`GAL_MOCK=1` 或模型不可用）**：纯算法生成一棵「大树」，无需模型：
  - 主干：`n1 → 场景链 → ……`
  - 每 `spine_step` 个节点挂一个 choice（key 分支）：2 条支线各走 `branch_len` 个场景，**汇合回主干同一个节点**
  - 全书均匀分布的 `flavor` 分支：2 条支线各 1~2 个场景，**汇合回分叉点的直接后继**
  - 最后一幕展开成 2~4 个结局（必须含 `true`）
  - 严格保证：节点数、分支层数、无断头、无环、全可达

> 兜底路径很重要：主人要能**不花一分钱**验证结构正确性。

### 5.5 骨架落盘（`app/agents/tools.py` 新增工具）

```python
async def write_skeleton(self, args, scope):
    """把整棵树的骨架一次写进图，落成真正的 Node（台词是占位句）。"""
```

- 入参：骨架 JSON（上面 `Skeleton` 的结构）
- 行为：
  1. 校验 `validate_skeleton()`
  2. 分配正式 id（`n1..nN`，按骨架顺序）
  3. 生成 `Node`：`status='pending'`、`lines=[占位]`、`bg` 用占位路径、`chars` 按 look 填、`pos` 自动排版（见 5.7）
  4. `_commit(nodes=..., agent_state=...)`，把骨架原文存进 `agent_state['skeleton']`（供续写复用）
  5. 返回 `{ok, nodes: N, edges: M, acts: K}`

**这是唯一的结构写入入口。**

### 5.6 填充（`app/agents/fill.py` + 新工具）

```python
async def fill_segment(self, args, scope):
    """给一批已有节点写台词，不许改结构。"""
```

- 入参：`chapter_id` 或 `node_ids`（一批 ≤ 20 个）
- 行为：
  1. 取这些节点的 `summary`（骨架里写的）当 brief
  2. 让模型产出 `lines[]`（每节点 1~6 句，单句 8~40 字，**不写句号**）
  3. **硬校验**：只能改 `lines` / `bg.prompt` / `chars[].mood` / `chars[].stance`；
     一旦试图增删节点或改 `choices`，直接 `ToolInputError('SKELETON_FROZEN', ...)`
  4. 写回后 `status='done'`

### 5.7 自动排版（新函数）

骨架节点没有坐标。`write_skeleton` 要自动排版：

- 按「层」排：`layer = 从 n1 到该节点的最短路径长度`；`x = 320 * layer`
- 同层内按出现顺序纵向排开，`y = 320 + index * 220`，超过 5 个折到第二列
- 排完保证没有两个节点坐标完全重合

（现有前端画布是 LiteGraph，坐标只是初始位置，用户能拖。）

### 5.8 续写（必须保留）

现有能力：进程被杀后重启，能从断点接着跑。
相关模块：`app/engine/checkpoint.py`、`app/engine/journal.py`、`agent_state['resume_plan']`。

- 骨架写入后，`agent_state['skeleton']` 就是续写锚点
- 重启后如果 `agent_state['skeleton']` 存在，**不要再生成骨架**，直接从「还有多少节点 `status != 'done'`」继续填充
- 骨架缺失（老项目）时，退化到旧流程或直接重生成骨架

## 10. 背景资料：主人原话（理解需求用）

> 「你那个自动节点分段还是很奇怪，特别是气氛分支分开后有一个节点后面啥都没连，
> 你直接在节点网里面不要分开了，直接有多少节点全部放在一个节点网里面，像大树一样，
> 我们直接完全重构全自动节点制作的后端。」

翻译成技术需求：

1. **节点网必须是一个整体**——所有节点在同一张图里，不许「这段在这章、那段在那章」割裂
2. **像大树**——主干清楚，分支从主干长出去，最后收回来或走向结局
3. **不许有悬空节点**——任何一条路走到底都不能「没东西了」

第 5 节的「骨架定死 → 填充」就是为这三条设计的：
- 骨架一次成树 → 节点网整体成型，不割裂
- 骨架里每个分叉都写明「从哪来、到哪去、在哪汇合」→ 大树形状
- 校验第 3 条「除 ending 外每个节点 to 非空」→ 从规则上禁止悬空
