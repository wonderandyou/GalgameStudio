# 任务：重做 GalgameStudio 的节点生成系统

> 你要重写的是「节点从哪来、怎么存、怎么校验、怎么播」这一整条链路。
> 不是加校验、不是打补丁，而是**换掉底层的节点模型和生成方式**。
>
> 项目在 `D:\软件\GalgameStudio`，FastAPI + 原生 HTML/JS，纯本地跑。
> 现在**能生成、能导出、能播**，但生成出来的图**结构是坏的**，播出来 27 个选项按钮糊满屏。
>
> 本文所有数字都是我（上一任维护者）**在真机真项目上跑出来的**，不是推测。
> 请把它们当成事实起点，不要重新猜。

## 0. 一句话说清要做什么

> **把「节点图」从「模型自由长的树」改成「代码保证的主干 + 会汇合的侧枝 + 旗标」，
> 并且让 `edges` 从存储字段降级为派生投影 —— 消除双真相。**

三件事，按顺序做，每件都能独立验收：

| # | 做什么 | 为什么 |
|---|---|---|
| **A** | 节点模型重定义 + `edges` 变成派生投影 | 现在同一张图有**两份互相打架的真相**，这是所有结构性 bug 的总源头 |
| **B** | 生成器改成「主干 + 汇合侧枝」，选项密度降到真实 galgame 水平 | 现在每 4.3 个节点就有一个选择，是真实 galgame 的 4~10 倍，必然指数爆炸 |
| **C** | 所有写入路径强制不变量 + 播放器不再信任脏数据 | 现在前端保存**只跑 pydantic**，语义不变量一条都没跑，坏图直接落盘 |

## 1. 现场证据（以下全部是实测输出，请原样采信）

### 1.1 出问题的项目

```
projects\p_04927612e8c44ec0b5519223a2a464e5\graph.json    128 节点
```

节点类型分布：

```
{'scene': 93, 'choice': 30, 'ending': 4, 'start': 1}      合计 128
```

### 1.2 `edges` 表严重冗余

```
edges total = 640    unique(from,port,to) = 114    冗余 = 526  (82%)
重复次数分布: {1: 72, 14: 22, 13: 20}
```

也就是说**同一根线被写了 13~14 遍**。

### 1.3 `start` 节点有 27 条出边

```
--- n1 的出边明细 ---
{'id': 'e53',  'from': 'n1', 'port': 0, 'to': 'n2'}
{'id': 'e95',  'from': 'n1', 'port': 0, 'to': 'n2'}
{'id': 'e96',  'from': 'n1', 'port': 1, 'to': 'n3'}
{'id': 'e137', 'from': 'n1', 'port': 0, 'to': 'n2'}
{'id': 'e138', 'from': 'n1', 'port': 1, 'to': 'n3'}
...（一路到 e599/e600）
```

注意两点：

1. **`start` 节点本该恰好 1 条出边，实际 27 条。**
2. **edge id 间隔恒定 42**：`e53 → e95 → e137 → e179 → … → e599`。
   42 是「一次完整写入产生的边数」，说明**每一轮写入都往同一个数组后面追加一份，从不替换**。

### 1.4 `choices` 数组被同样地追加了 13 遍

30 个 choice 节点的选项数分布：

```
{2: 19 个,  4: 1 个,  26: 10 个}
```

那 10 个长度 26 的节点，内容长这样：

```
n44 '问日期'  len=26
   0 '看清日期'     -> n2      1 '先说十年前' -> n3
   2 '看清日期'     -> n2      3 '先说十年前' -> n3
   ...（一直重复到 25）
```

**26 = 2 个真选项 × 13 遍。** 不是模型编了 26 个选项，是同一组被复制了 13 次。

### 1.5 播出来就是一屏按钮

`ui/app.js` 的播放器：

```js
function choiceTargets(n) {
  const ls = links.filter((l) => l.from === n.id) ...   // ← 读 links，不读 n.choices
  return ls.map((l, i) => ({ label: labels[i] || ('选项 ' + ...), to: l.to }));
}
```

`links` 里这个节点有 27 条边 → 渲染 27 个按钮 → 960px 高的容器里露出 12 个，剩下的滚出屏幕。
（本项目 `n44` / `n48` / `n52` / `n56` / `n60` / `n64` / `n68` / `n72` / `n76` / `n80` 都是这个状态。）

**所以「一屏十几个选项」不是模型编的选项多，是 `links` 里同一个出口堆积了十几份。**

### 1.6 顺带一个独立漏点：「选项 C」「选项 D」是从哪来的

截图里出现字面量「选项 C」「选项 D」，这不是模型生成的文字，是**画布的默认占位标签**：

```js
// ui/graph-editor.js:836
node.properties.choiceLabels = ['选项 A', '选项 B', '选项 C', '选项 D'];

// ui/app.js:1431
n.choices = [{ label: '选项 A', to: '' }, { label: '选项 B', to: '' }];
```

画布为了让分支节点「先画出来 4 个出口」，会给 `choices` 补上占位标签。
**但保存时这些没填过的占位项没有被过滤掉，直接当真实选项写进了图**，
于是玩家在游戏里看到「选项 C」。

修法：`buildGraphPayload()` 里 `base.choices = mapped` 那步，
要把 `label` 匹配 `^选项 [A-D]$` **且** `to` 为空的项一起丢掉（现在只丢了 `to` 为空的）。
更好的做法是给占位项加显式标记 `placeholder: true`，保存时按标记丢，不靠文字猜。

> 这条虽然小，但它说明同一个病根：**画布的工作态数据（占位、临时值）没有和产物数据分开。**

## 2. 根因（四条，与证据一一对应）

### 根因一：双真相 —— `edges` 和 `choices` 都在存「连接」

`app/engine/graph.py` 自己的 docstring 就写了「`graph['edges']` 是 `choices` 的投影」，
但**没有任何代码强制这一点**。结果两条真相各自演化，然后打架。

而且两边**连边的 id 规则都不一样**：

| 位置 | 生成方式 | 实际落盘的 id |
|---|---|---|
| `app/engine/graph.py:56` 后端 | `id=f'e_{n["id"]}_{i}'` | `e_n43_0` / `e_n86_1` |
| `ui/app.js:3932` 前端 | `id: l.id \|\| ('e' + (i + 1))` | `e53` … `e640` |

**这张图里两种 id 同时存在，比例是决定性的：**

```
符合后端 e_{nid}_{i} 格式：  52 条     （e_n43_0, e_n86_0, e_n86_1, ...）
符合前端 e{数字}   格式： 588 条     （e53, e54, ... e640，完全连续）
                              ─────
                              640 条
```

`588 = 14 × 42`。**前端一共保存了 14 次，每次都把「本章的 42 条边」原样追加了一遍。**

> 所以这张图最初只有 **52 条边**（后端生成的那份），
> 剩下 588 条全是前端 14 次保存叠出来的残影。

### 根因二：前端保存路径的合并逻辑无去重

`ui/app.js:912`（章节视图同步）：

```js
links = links.filter((l) => !(visible.has(l.from) && visible.has(l.to))).concat(d.links);
```

「先过滤掉两端都在本章的旧边，再把本章的边 concat 进来」——
**两端有一端在章外的旧边不会被过滤，会被重复保留；而且全程没有按 `(from, port, to)` 去重。**

实测这 588 条冗余正好是 `14 × 42`：**每保存一次，本章的 42 条边就被追加一遍**，
存了 14 次。这不是偶发，是**每次保存都必然发生一次**。

### 根因三：保存接口只跑 pydantic，不跑语义不变量

`app/mock_api.py:925`：

```python
@router.put('/projects/{project_id}/graph')
async def save_graph(project_id: str, body: dict):
    """前端保存画布（拖动位置等）：只存不生成，按契约 §3.6 校验结构。"""
    ...
    try:
        Graph.model_validate(body)      # ← 只校验字段类型/必填
    except ValidationError as exc:
        ...
    await jobs.persist(atomic_json, root / 'graph.json', body)   # ← 原样落盘
```

`validate_graph()` 里明明有这些检查：

```python
if sorted(actual) != sorted((e['from'], e['port'], e['to']) for e in expected):
    raise ValueError('edges 与 choices 不一致')          # graph.py:103
```

但**保存路径根本没调它**。所以 `start` 27 条出边、choice 26 个选项，全部畅通无阻写进磁盘。

同理 `app/agents/tools.py:1457` 有 `if not 2 <= len(choices) <= 4:` 的检查，
但它只在 **writer 自己的章节作用域**里跑，前端那条路完全绕开。

> **一句话**：校验器是有的，但**装在一条没人走的路上**。

### 根因四：生成器的故事形状是「树」

`app/agents/outline.py` 的 `build_template()` 现在建出来的是一棵树：
每个分支都长出自己的子树，深度上限 2。

树的问题是数学上的：**分支数 × 每支节点数 = 总节点数**，而树里的叶子**必然断头**
（叶子要么是 ending，要么就是死路）。为了让叶子不是死路，就得让每个叶子都成为 ending，
于是 `ending` 数量爆炸；不爆炸就只能留断头。

**真实 galgame 不是树，是「主干 + 会汇合的侧枝」（branch & recombine）。** 见第 3 节。

## 3. 正经 galgame 是怎么做的

以下依据 Ren'Py 官方文档（业界事实标准，绝大多数日式 galgame 的脚本模型都是这一套的变体）：

- [Quickstart — Ren'Py Documentation](https://www.renpy.org/doc/html/quickstart.html)
- [Branching & Recombining the Story](https://sources.debian.org/data/main/r/renpy/6.10.2.dfsg1-1/doc/tutorials/Branching_%26_Recombining_the_Story.html)
- [Remembering User Choices](https://sources.debian.org/data/main/r/renpy/6.6.2.dfsg1-1/doc/tutorials/Remembering_User_Choices.html)

### 3.1 Ren'Py 的完整最小模型，就 6 个概念

| Ren'Py 语句 | 语义 | 我们这边的对应 |
|---|---|---|
| `label start:` | 一个**全局唯一**的命名位置 | `node.id`（唯一） |
| say statement | 一句台词 | `node.lines[]` |
| `scene bg meadow` / `show sylvie smile` | 换背景 / 摆立绘 | `node.bg` / `node.chars[]` |
| `menu:` + 缩进块 | 一个选项点，每个选项是一个代码块 | `type='choice'` + `node.choices[]` |
| `jump label` | 跳转 | `choices[].to` |
| `default x = False` / `$ x = True` / `if x:` | **旗标**：记住玩家选了什么，后面据此分岔 | **我们现在没有，这是缺的** |
| `return` | 结束 | `type='ending'` |

### 3.2 关键机制一：Branch & Recombine（分支必须汇合）

官方教程原文示例：

```renpy
menu:
    "It's a videogame.":
        jump game
    "It's an interactive book.":
        jump book

label game:
    m "It's a kind of videogame..."
    jump marry          # ← 汇合

label book:
    m "It's like an interactive book..."
    jump marry          # ← 汇合

label marry:            # ← 两条支线都回到这里
    "And so, we become a visual novel creating duo."
```

**这是 galgame 分支的标准写法：分出去 → 走一小段 → 回到主干。**
官方还专门说了「除非这条支线一直走到游戏结束，你不然会想让支线再跳回去」。

> 这直接说明：**「分支的终点必须是汇合点或结局，不能是断头」不是一句建议，是 galgame 的构造规律。**

### 3.3 关键机制二：选项的后果存在旗标里，而不是存在拓扑里

```renpy
menu:
    "Buy her an Iguana":      $ gift = "iguana"
    "Buy her a Corn Snake":   $ gift = "corn snake"
    "Buy her a tortoise":     $ gift = "tortoise"

# 很久以后
if gift == "iguana":
    m "Oh Bob, I've always wanted an iguana!"
```

以及好感度累计的写法：

```renpy
$ strength_points += 1
...
if strength_points > max(dexterity_points, mad_science_points):
    "You pick up a cow and jump over the moon."
```

**这是最重要的一条认知**：真实 galgame 里，**绝大多数选项不改变图的拓扑**，
它们只改旗标；真正改变拓扑（跳进别的路线）的选项很少。

所以真实游戏里「两个选项指向同一个后续节点」是**完全正常的**——
那叫「气氛选项 / cosmetic choice」。
（反过来说：`choices[].to` 互不相同**不该**作为硬性要求。
现在 `tools.py:1460` 的 `len({c['to'] for c in choices}) != len(choices)` 这条是错的，
它会把合法的气氛选项判成非法。）

### 3.4 关键机制三：label 必须全局唯一

官方原文：「Please note that labels have to be unique within a Ren'Py script.」

我们的历史日志里出现过 `骨架节点 ref 重复：k161` ——
**这等于生成了一个 Ren'Py 编译不过的脚本。**

### 3.5 关键机制四：发布前必须 lint

官方 Quickstart 的 Releasing 步骤里，「Check the Script (Lint)」是独立一步。
我们对应的就是 `validate_graph()` —— 但它必须**在每次写入时都跑**，不是只在导出时跑。

### 3.6 真实 galgame 的形状特征（设计参数）

| 指标 | 真实 galgame | 我们现在 | 结论 |
|---|---|---|---|
| 选项密度 | 大约每 15~40 个节点一个选择点 | 30/128 ≈ **每 4.3 个** | 高了 4~10 倍 |
| 每个选择的选项数 | 2~3 个为主，4 个算多 | 出现 26 个 | 必须硬上限 |
| 分支结构 | 主干 + 短侧枝 + 汇合 | 树 | 必须换 |
| 分支深度 | 深层树极罕见（通常 ≤2 层分叉） | 上限 2 但靠 depth 变量 | 概念对，实现要落到「汇合」上 |
| 结局数 | 3~6 个，分开命名/编号 | 4 个 | 合理 |
| 无选项单结局 | 叫 Kinetic Novel | — | 允许，但要显式声明 |

## 4. 新数据模型

### 4.1 唯一真相：`nodes` 存，`edges` 算

**`edges` 从存储字段降级为派生投影。** 这是第 0 节 A 项的核心。

规则：

1. `graph.json` 落盘时，`edges` **可以写可以不写**，但**读回来时一律忽略磁盘上的值**，
   用 `edges_from_nodes(nodes)` 重算。
2. **任何从客户端进来的 `edges` 直接丢弃**，不参与合并、不参与比较、不参与校验。
3. 任何返回给客户端的图，`edges` 都是刚算出来的那一份。

建议实现（不是必须照抄，但语义必须一致）：

```python
# app/engine/graph.py

def normalize_graph(graph):
    """把任意来源的图洗成唯一真相的形状：edges 永远是 choices 的投影。"""
    nodes = graph.get('nodes') or []
    out = {k: v for k, v in graph.items() if k != 'edges'}
    out['edges'] = edges_from_nodes(nodes)
    return out
```

然后在**每一个入口**调它：保存接口、读取接口、导出、checkpoint 恢复、agent 提交、
以及 `public_graph()`。

> 这一条改完，根因一、根因二**在数学上不可能再发生** ——
> 因为重复的边根本没有地方寄存，每次都是重算。

### 4.2 节点 id 规则

**硬要求只有一条：全局唯一。** 剩下的可选。

推荐格式（新项目用）：

```python
NODE_ID = re.compile(r'^[sc]\d{3}$|^e\d{3}$')     # s001 / c007 / e003
```

- `s` = scene（含起始）、`c` = choice、`e` = ending
- 3 位数字，同类内单调递增
- **id 由生成器在创建节点时分配，不由模型指定**

⚠️ **迁移警告（很重要，别踩）**：现在磁盘上的所有项目用的都是 `n1 … n128`。
如果你直接加一条「id 必须是 `s001` 格式否则拒绝」，
**会把主人手头所有旧项目全部打死，一个都打不开。**

所以：

| 场景 | id 规则 |
|---|---|
| 新建项目 | 用推荐格式 |
| 读旧项目 | **只校验唯一性，不校验格式**，原样保留 `n1` |
| 旧项目改 id | ❌ 不要自动迁移。id 变了等于图变了，`checkpoint`、`agent_state.nodes`、导出产物全部对不上 |

**唯一性由写入路径保证，而不是靠「撞了再重试」。**
具体做法：生成器分配 id 时用一个 `next_id` 计数器，从当前最大值 +1 开始，
**永不回退、永不复用**。删掉的 id 也不回收 —— 复用 id 会让旧 checkpoint 指错节点。

> 另外建议**顺手消灭 `ref` / `id` 双轨制**：
> 现在模型写 `ref`，代码再映射成 `id`（`app/agents/tools.py` 里的 `by_ref` / `by_id` 两套索引）。
> 历史上 `骨架节点 ref 重复：k161` 就是这个双轨制漏出来的。
> **如果能让模型完全不碰 id/ref（id 由代码分配，模型只按顺序拿到节点），就彻底没有重复问题。**

### 4.3 节点类型与出边数（**硬不变量**）

| type | 出边数 | 说明 |
|---|---|---|
| `scene`（含 `s001` 起始节点） | **恰好 1** | 单一出口，天然不会分叉 |
| `choice` | **2 或 3**（关键点允许 4） | 每个出口一个选项 |
| `ending` | **0** | `end_kind ∈ {true, good, bad, alt}` |

> 注意 `start` 不再是独立类型 —— **起始就是第一个 `scene`**。
> 理由是现在的 `start` 类型既要「唯一」又要「恰好一个出口」，在合并逻辑里被特殊对待了十几处，
> 是 bug 温床（证据：它长出了 27 条出边却没人拦）。
> 如果你评估后认为保留 `start` 类型代价更小，可以保留，但**必须满足同样的出边数不变量**。

### 4.4 choice 的字段

```jsonc
{
  "id": "c007",
  "type": "choice",
  "title": "问日期",                 // 这个选择点的一句话
  "kind": "key",                     // key = 会改拓扑 / cosmetic = 只改旗标
  "lines": [ ... ],                  // 选择点之前的那段台词
  "choices": [
    {
      "label": "看清日期",
      "to": "s012",
      "effects": { "knows_date": true },       // 旗标写入（cosmetic 必须有）
      "condition": null                        // 可选：条件显示
    },
    {
      "label": "先说十年前",
      "to": "s012",
      "effects": { "told_past": true },
      "condition": null
    }
  ]
}
```

要点：

- **`kind='cosmetic'` 的 choice，所有选项 `to` 指向同一个节点**（这是合法的，别再拦）
- `port` 就是选项下标 `0..n-1`，**必须连续无空洞**
- 一个出口 `(from, port)` **只能有一条边**（这是去重的正确键）

### 4.5 旗标（flags）

```jsonc
// graph 顶层
"flags": {
  "knows_date": { "type": "bool", "default": false },
  "affection": { "type": "int",  "default": 0 }
}
```

**本阶段只要求：**
- `choices[].effects` 能被存下来、被播放器应用
- `condition` 能读旗标决定「这个选项显不显示」

**不要求**（明确排除，别做）：条件分支的图拓扑（`if` 导致跳不同的节点）。
那一层等旗标跑通了再说，现在做会把范围撑爆。

## 5. 新生成器：主干 + 汇合侧枝

### 5.1 结构模板（代码造，模型只填词）

**和现在一样的原则**：`build_template()` 用纯代码定死拓扑，模型只填
`title` / `summary` / `choices[].label` / `lines`。

核心不变量测试必须保留并加强：

```python
assert topology(skeleton) == topology(template)
```

### 5.2 形状算法

把整局游戏当成**一条主干**，加**若干会回来的侧枝**：

```
s001 ─ s002 ─ s003 ─ c004 ─┬─ s005 ─ s006 ─┐
                            │                ├─ s010 ─ s011 ─ c012 ── ...
                            └─ s007 ─ s008 ─┘         │
                                                      ├─ s013 ─ s014 ─┐
                                                      │                ├─ s020 ─ ...
                                                      └─ s015 ─ s016 ─┘
```

参数（全部可配，给默认值）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `total_nodes` | 180 | 目标节点总数 |
| `chapters` | 9 | 章数 |
| `choice_density` | 0.06 | 选择点 / 总节点（≈每 17 个一个） |
| `branch_len` | 3~6 | 每条侧枝走几个节点后汇合 |
| `rejoin_max` | 10 | **硬上限**：侧枝必须在这么多节点内汇合 |
| `depth_max` | 2 | 最多嵌套几次分叉 |
| `endings` | 4 | 结局数（1 true + 2 good/bad + 1 alt） |

### 5.3 侧枝必须汇合 —— 这是新增的硬不变量

从 `choice` 的任意一个出口出发，沿唯一路径前进，必须满足：

> **在 `rejoin_max` 步内到达一个「入度 ≥ 2 的节点」（汇合点），或到达 `ending`。**

实现建议：

```python
def check_rejoin(nodes, choice_node, rejoin_max=10):
    indeg = Counter(e['to'] for e in edges_from_nodes(nodes))
    problems = []
    for c in choice_node['choices']:
        cur, steps = c['to'], 0
        while steps < rejoin_max:
            n = by_id.get(cur)
            if n is None:
                problems.append(f'{c["label"]} 指向不存在的 {cur}'); break
            if n['type'] == 'ending':
                break                      # 走到结局，合法
            if indeg[cur] >= 2 and steps > 0:
                break                      # 汇合了，合法
            outs = n.get('choices') or []
            if len(outs) != 1:
                problems.append(f'{c["label"]} 在 {cur} 又分叉，超范围'); break
            cur = outs[0]['to']; steps += 1
        else:
            problems.append(f'{c["label"]} 走了 {rejoin_max} 步还没汇合')
    return problems
```

**这条不变量成立，图就永远不会长出断头，也不需要任何「事后修复」。**

### 5.4 选项密度和分支数要算出来，不是碰出来的

```
选择点数 = round(total_nodes × choice_density)      # 180 × 0.06 ≈ 11 个
每个选择 2~3 个选项
侧枝节点数 ≈ 选择点数 × (branch_len - 1)            # 11 × 4 ≈ 44
主干节点数 = total_nodes - 侧枝节点数
```

**先算数，再建图。** 现在的代码是「建完再数一遍够不够」，所以才会有
`骨架节点数 150 超出目标 100 的 ±10%` 这种要重试的失败。

### 5.5 结局挂在哪

结局只从**主干末尾**和**关键选择（`kind='key'`）的末端**长出来，
不从侧枝中段随便长。这样保证：

- 每条侧枝都能汇合回主干（不会被迫变成结局）
- 结局数量可控（= 主干的收束数）

## 8. 已经试过并失败的方案（**别再走这两条路**）

这两条都是我亲手试过、亲手回滚的，别浪费时间去验证。

### 8.1 ❌ 事后结构修复（`_fix_dangling` / `_fix_unreachable`）

试过：图长完发现断头，自动给断头节点补一条边。

### 8.2 ❌ 用一堆硬校验去拦模型的主观猜测

## 10. 附：一句话总结给你的设计判断

> **真实 galgame 的分支是「出门走一小段，然后回家」，不是「一直往下长」。
> 我们的生成器一直在往下长，所以它必然长成一棵会断头的树。
> 把它改成「一定会回家」，断头问题就从「要修」变成「不可能发生」。**
