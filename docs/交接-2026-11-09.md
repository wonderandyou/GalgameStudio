### ~~P1 · 立绘按「表情 × 动作」差分~~ ✅ 已完成（第 467 轮，实现见第 10 节）

**问题描述**：项目「了」510 个节点，立绘只有 **3 张**（一个角色从头到尾一张脸）。
数据其实都在：`pose_prompts` 482/510 节点非空、`mood` 有 145 种、`library.py` 里
`POSE=5 种`、`MOOD=7 种`、`BUDGET.pose_per_char=12`。

**根因**：`list_pending_assets` 是按角色列的：

```python
# app/agents/tools.py 约 1483 行
poses = [dict(key=c['id'], ...) for c in self.graph['characters']]
```

`key` 直接是角色 id，没有姿态和表情维度；`generate_image` 也只用 `base_key(char_id)`。
`library.pose_key()` 是**死代码**（定义了但没被调用）。

**改法四步**

1. 编剧排产（`loop.py` 的 `direct_production` / `production_plan`）里加立绘清单：
   每个角色 → `[{pose, mood, prompt, node_ids, priority}]`
2. `list_pending_assets` 按这张表列（不是按角色列一条）
3. `generate_image` 支持 `char:<id>:<pose>:<mood>` 这种 key
4. 出图顺序：先 base（直出透明）→ 再差分（以 base 作 reference_images 做 I2I，透明会自动继承）

**代价**：140 节点的项目立绘从 2 张变 **20~30 张**，生图时间和费用按张数走。

## 6. 约定与坑（都是踩过的，别再踩）

### 改了前端必须做

1. **`ui/*.js` 或 `ui/*.css` 改动后，要把 `ui/index.html` 里的 `?v=...` 换一个值**
   否则 Edge 会用缓存，改了等于没改。
2. 验证必须走真界面（CDP + Edge），不能只看代码。

### 测试用 Edge 的坑

- **用 PowerShell 的 `Start-Process` 起 Edge**，不要用 Python 的 `subprocess.Popen` ——
  后者会被作业对象连坐回收，表现是「调试端口刚通就拒连」。
- 用**随机端口**（比如 9741~9799），别固定 9222，容易撞上残留实例。
- 用完记得杀：`Get-CimInstance Win32_Process -Filter "Name='msedge.exe'" | ? { $_.CommandLine -match '--remote-debugging-port=' } | Stop-Process -Force`

### 素材与凭据的位置

- **凭据在项目 `.state/credentials.json`**（DPAPI 加密），不是 `%LOCALAPPDATA%\GalgameStudio`。
  `Credentials()` 默认读后者，读不到会返回全默认值 → 表现成「没配 key」，很容易误判。
- **项目数据在 `projects/<p_id>/`**，`projects/` 在 `.gitignore` 里（不进 git）。
- 立绘原图备份在 `projects/<id>/assets/_backup_立绘原图_<时间戳>/`。

### 跨源 canvas 会污染

素材走 `8790/api/assets`，页面在 `8799`，是跨源。要在浏览器里读像素，
`Image` 必须设 `crossOrigin = 'anonymous'`，否则 `getImageData` 抛
`The canvas has been tainted by cross-origin data`（会**静默失败**，很坑）。

### 生图 / 配音的现状

- 生图：`qwen-image-3.0-pro`（RGB，写实好） / `qwen-image-2.1-pro`（**能出透明底**，画风偏插画）
- 配音：`qwen3-tts-flash`，可用音色 `Cherry / Serena / Ethan / Chelsie / Dylan / Jada / Sunny / Nofish`
  （**`longxiaochun` 是 CosyVoice 的老名字，会 400**，已被代码兜底）
- 两边都要走阿里云百炼官方

## 9. 第 466 轮：界面风格设计（P0 已完成）

### 做了什么

打包页（`data-pgo="export"` 那一页）多了一张「界面风格」卡片：要求输入框 + 参考图上传/拖拽
+ 「设计哪块」三选一 + 「设计界面」按钮 + 预览结果区。**完全没有碰原来的导出流程**
（`runPack` / `btnPack` / 图标逻辑一行没动），设计失败不可能把成品弄坏。

后端新增一个接口 + 一个 agent 工具，走「**生成新预设 → 复用现有 render 渲染**」这条路：

| 层 | 文件 | 内容 |
|---|---|---|
| 设计核心 | `app/ui_presets/design.py`（新） | 取色 / 解读要求 / 合成预设 / 落盘 |
| 预设加载 | `app/ui_presets/__init__.py` | `_load_all()` 加扫 `designed/` 子目录；导出 `run_design` 等 |
| 渲染兜底 | `app/ui_presets/render.py` | 新增 `_skeleton_id()`：自定义预设按 `base` 用内置四套的骨架 |
| 工具 schema | `app/agents/tool_schema.py` | UI agent 加 `design_ui` |
| 工具实现 | `app/agents/tools.py` | `design_ui()`：设计 + 渲染 + 登记 `agent_state.ui_style` |
| HTTP | `app/mock_api.py` | `POST /api/projects/{id}/ui/design`；`/api/assets` 后缀放行 `.html` |
| 技能文档 | `app/skills/ui/04-design.md`（新） | agent 怎么用 `design_ui`、哪些做不到 |
| 前端 | `ui/index.html` / `app.js` / `api.js` / `app.css` | 卡片、压缩上传、调用、结果渲染 |

### 接口

```

{ "requirement": "江南雨夜，水墨古风；标题要大", "references": ["data:image/png;base64,..."],
  "target": "both", "base": "" }          # 四项都能省
→ { ok, preset:{id,name,vibe,base,palette,notes,file},
    screens:[{screen,relative,url,bytes}],       # url 走 /api/assets，iframe 预览用
    analysis:{colors,matched,contrast,references_used}, unsupported:[...] }
```

**只写 `assets/ui/rendered/*.html` 和 `app/ui_presets/designed/*.json`，不碰
`graph.json`、不碰 `export/`** —— 测试里专门断言了「设计前后节点数不变」。

### 设计要求里哪些真生效

配色（参考图取色）、明暗主题、标题字体、标题字号、字距、立绘开关、圆角。
`design.py` 的 `_TYPO_RULES` / `_CHARACTER_WORDS` / `_FONT_RULES` / `_RADIUS_RULES` 是唯一真相。

**菜单排列（竖排 / 横排 / 编号）改不了**：四套骨架的菜单排列是写死在 `render.py` 的 CSS 里的，
`layout.menu` 这个参数渲染时根本不读（`tweak_ui_preset` 的 `menu` 参数同样是死参数，这是既存问题）。
所以用户要求了这几项时，`unsupported` 会如实返回，**不许假装改了**。要真做，得改 `render.py` 给
`.menu` 加一层覆盖 CSS —— 四个骨架的定位/书写模式都不同，风险不小，留作后续。

### 本轮踩的坑（都别再踩）

| 坑 | 症状 | 原因 / 正确做法 |
|---|---|---|
| **Edge 在 DSH 沙箱里起不来** | `FATAL:mojo\public\cpp\platform\platform_channel.cc:187 Check failed: 拒绝访问 (0x5)`，起来 3~8 秒就死 | 浏览器多进程靠 **Windows 命名管道**通信，DSH 的 workspace-write 沙箱不许开命名管道。`--no-sandbox` / `--single-process` / `--no-zygote` 都绕不过。**要用 jsdom 或让主人在沙箱外看** |
| `isinstance(False, int)` 是 **True** | 「不要立绘」算出来 `show_characters = 41` | bool 是 int 的子类，`isinstance(change, bool)` 必须排在 int 前面 |
| 子串否定 | 「**不要**立绘」里含「要立绘」，两条规则互相覆盖翻成 True | 立绘开关单独用正则判（`_character_toggle`），不塞进顺序规则表 |
| 取色取到桶中心 | 米白 `(228,222,206)` 变粉白 `(240,208,208)` | 量化桶要记**桶内 RGB 的平均值**，不是桶中心 |
| 深色被当纯黑删掉 | 深蓝夜空 `#161c28` 被丢掉，`bg` 用了混色点 | 判纯黑/纯白看**通道极值**（`max≤10` / `min≥246`），不要用亮度阈值（`#161c28` 亮度只有 0.013） |
| 混色点当底色 | `bg = #4f2c28`（说不清的脏红） | 缩放时块边界的混色权重只有 1~2%，用 `_main_colors()` 只留够面积的色 |
| 强调色被推成灰白 | 暗红 `#6c3428` → `#e5dbd8` | 贴同系底色对比度不够时用 `_ensure_contrast(minimum=2.2)` **只推到刚好够**，别固定推到亮度 0.72 |
| `safe_asset` 只放行 `assets/` | 预览 URL 400 `INVALID_ASSET_PATH` | 渲染产物必须写 `assets/ui/rendered/`，写 `ui/rendered/` 拿不到 |
| 自动挑骨架挑到自己 | 第二次设计时骨架变成上次的 `designed-xxx` | `_pick_base` 只在**内置四套**（`ORDER`）里挑，否则越设计越偏 |
| npm 装包被沙箱拒 | `The operation was rejected by your operating system` | npm 的 cache 默认在 `%LOCALAPPDATA%`，要 `--cache <工作区内路径>` |

## 12. 「百炼 TTS 连不上」的真相（第 469 轮已修）

### 症状

配音阶段报连不上。很容易误判成「百炼服务挂了 / 网络不通 / key 过期」。

### 实测澄清

**百炼网络完全正常**，用 Python 直连：

```
dashscope.aliyuncs.com
  DNS   : 8.140.217.18 / 39.96.198.249 / 8.152.159.24 / 39.96.213.166
  TLS   : OK  TLSv1.3  证书 *.aliyuncs.com（Alibaba (China) Technology Co., Ltd.）
  HTTP  : 401 {"code":"InvalidApiKey","message":"No API-key provided."}
```

返回 401 是**健康状态**：能连上、能握手、服务器认得你，只是没带钥匙。

### 真正的根因

`app/providers/local_tts.py` 的 `is_available()` **漏了 `enabled` 判断**：

```python
def is_available(self):
    """能不能真调：启用状态 + 凭据是否齐。"""   # ← 注释说要查启用状态
    if not self.base:
        return False
    return True                                  # ← 代码压根没看 self.enabled
```

于是配置里明明 `enabled=False`、服务也从没启动过的 `local_tts` 被判成**可用**。

而 `STAGE_KINDS['voice'] = ('bailian_tts', 'local_tts')`，百炼没 key 也不可用 →
**voice 阶段就只剩这条假可用的本地通道**，每次配音都去连 `http://127.0.0.1:9880`
然后失败。

界面上看到的「百炼 TTS 连不上」，**实际连的是本地 9880 端口**。

### 修法

`is_available()` 先看 `enabled`：

```python
if not self.enabled:
    self._reason = '未启用'
    return False
```

修完 `registry.choose('voice')` 变成正确结果：

```
provider=None   reason='bailian_tts: 未启用；local_tts: 未启用'
```

也就是「没配 key → 语音阶段降级成静音占位，并把原因写进日志」，
而不是「去连一个没跑的服务然后报错」。

### 怎么真正用上百炼配音

`.state/credentials.json` 的 `bailian_tts` 填 `api_key`，界面保存一次即可。
其它参数已经是**对的值**，不用改：

| 项 | 值 |
|---|---|
| `base_url` | `https://dashscope.aliyuncs.com` |
| `model` | `qwen3-tts-flash` |
| `voice` | `Cherry`（可用：Cherry / Serena / Ethan / Chelsie / Dylan / Jada / Sunny / Nofish） |
| `speed` | 0.92 |

`longxiaochun` 是 CosyVoice 的老音色名，用它会 400 —— 代码里已有兜底回退。

### 顺带修好的 4 个测试

这个 bug 一直挡着 4 个「没 key 时应该降级」的测试，修完它们自己就绿了：

- `test_mock_off_degrades_to_mock_when_no_keys`

### 12.1 补：界面「测试连接」报 `Only Uris starting with 'ws://'`

主人配了 key 之后点测试，界面上是红字：

> `Only Uris starting with 'ws://' or 'wss://' are supported.`

**不是 key 的问题，也不是网络的问题**，是测试按钮用错了协议。

`app/providers/probe.py` 的分支是：

```python
elif kind == 'qwen_image':
    ...
else:                                   # ← bailian_tts 落进最后的 else
    from .websocket_probe import handshake
    await handshake(base, cfg['api_key'])
```

**bailian_tts 不管配的是 `https://` 还是 `wss://`，一律走 WebSocket 握手。**
而项目默认配置是 `https://dashscope.aliyuncs.com` + `qwen3-tts-flash`（HTTPS 模型），
拿 https 去建 WebSocket，DashScope 就回那句「只支持 ws://」。
看起来像「百炼连不上」，其实是测试走了错协议。

修法：按协议分流 —— `base_url` 以 `ws` 开头才走握手，否则走 HTTPS 的
`/compatible-mode/v1/models` 鉴权。

验证（`_qa/_test_tts_probe.py`，用假 key 打真接口，不花钱）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| https + qwen3-tts-flash + 假 key | `Only Uris starting with 'ws://'` | `HTTP 401 Incorrect API key provided` ✓ |
| https + 空 key | — | 本地拦住：「请先配置 API key」 |
| wss + CosyVoice | 握手 | 仍然握手（没被误当成 HTTP） |

⚠ **注意**：`probe.py` 只负责「测试连接」，**改完要重启后端**才生效。
另外 `.state/credentials.json` 里 `bailian_tts.api_key` 目前仍是空的 ——
界面表单里填了 key 只是**测试时临时用**，**必须点保存**才会落盘，
生成流程是从磁盘读配置的。

| 环节 | 做法 | 位置 |
|---|---|---|
| 写盘 | **原子写**：临时文件 → flush → fsync → `os.replace`（同分区原子），失败重试 5 次（20/40/60/80ms） | `app/store.py::atomic_bytes` |
| 图损坏 | 读不出来时**自动回滚到快照**，并把坏文件留成 `graph.broken-*` | `mock_api.py:196-216` |
| 重新生成前 | 图里已有内容（节点>1 或有完成的章）时，**先备份** `graph.before-restart-YYYYMMDD-HHMMSS.json`，再清空重写 | `mock_api.py:382-392` |
| 任务续跑 | 启动时 `jobs.restore()`：`.jobs/j_*.json` 里 `queued`/`running` 且最后事件不是 `done` 的，**重新跑一遍** | `mock_api.py:642-654` |

### 「重启后项目变莫名其妙」的三个真实原因

**① 生成从来没成功过（主因）**

主人 22:46 那次的端到端证据（`.jobs/j_58874c3b...json` 的 error 事件原文）：

```
code    : SKELETON_INVALID
message : 骨架节点数 150 超出目标 100 的 ±10%
where   : writer.outline
```

骨架卡在校验就抛错，**骨架根本没落盘**，图停在初始的「起点 + 结局」2 节点空壳。
查遍所有 `graph.before-restart-*.json`，**没有一个超过 2 节点** —— 也印证了这点。

（这个错已在 §13 修掉。）

**② 点一次「新建」实际建了两个项目**

`index.html` 里有两个按钮**共用了同一个 id**：

```html
101: <button id="btnNewProject">新建项目</button>   <!-- 项目页 -->
485: <button id="btnNewProject">新建项目</button>   <!-- 编辑器工具栏 -->
```

`getElementById` 只返回第一个，于是 `app.js:663`（`createProjectFromInput`，用输入框的名字）
和 `app.js:1448`（`newProject`，用「未命名 MM-DD HH:MM」）**两个监听全落在项目页那个按钮上**：
点一次 → 建两个（一个叫「5」，一个叫「未命名 11-09 22:16」）。
而工具栏那个按钮**从来没绑上**，点了没反应。

实测证据：`p_f974799…`（未命名 11-09 22:16）与 `p_38052ad6…`（5）
的 `created_at` 分别是 `14:16:04.781052` 和 `14:16:04.780046`（UTC）—— **相差 1 毫秒**。
项目列表里 30 个同名「雨停之前」也全是成对出现，同一根因。

**修法**：工具栏按钮改用独立 id `btnNewProjectTb` 并单独绑定；
项目页按钮只保留 `createProjectFromInput` 一处监听。

**验证**（`_qa/_test_dup_id.js`，jsdom 解析真实 HTML）：

| 检查 | 结果 |
|---|---|
| 全文档 185 个 id 是否唯一 | **无重复** ✓ |
| `#btnNewProject` / `#btnNewProjectTb` 是两个元素 | ✓ |
| `btnNewProject` 的 click 监听数量 | **1** ✓ |
| `btnNewProjectTb` 的 click 监听数量 | **1** ✓ |
| 旧的「btnNewProject → newProject」写法 | 已绝迹 ✓ |

**③ 我让他重启时没说清后果**

生成到一半重启：已落盘的进度**不会丢**（原子写 + 快照），
但**在跑的任务会从内存里消失**，`jobs.restore()` 会把它**从头再跑一遍**。
这一点当时没提醒，属于沟通疏漏。

### 教训（给以后的我）

- 让主人重启前，**先确认有没有正在跑的任务**；有的话先停、先说清「重启会从头上跑」。
- 报「装好了 / 修好了」之前，先把**同类地方**（同 id、同函数、同绑定）扫一遍，
  别只修眼前那一处 —— 这两个按钮的 id 冲突存在很久了，一直没人扫。

## 15. 填充阶段「节点不匹配」的三连 bug（第 472 轮）

### 背景：骨架已经通了

§13 放宽节点数之后，主人重跑「5」，日志显示骨架这关**真的过了**：

```
23:37:42  正在生成整图骨架，目标 88 个节点
23:38:22  [检查点 ck-000021 落盘：节点=88，骨架节点=88，201 KB]
23:38:31  error: 填充返回的节点与请求的待填节点不匹配
```

**88 节点的完整骨架就在 `checkpoints/ck-000021.json` 里**（201,927 字节，骨架齐全）。
也就是说：骨架生成、校验、冻结、落盘全都成功了，**死在下一阶段第一步**。

### 三个连锁 bug

**① `_checked_fill_updates` 要求 id 集合完全相等，且用致命错误码**

```python
set(pending) <= set(supplied) <= set(selected)   # 少一个、多一个、错一个都算
→ 'SKELETON_FROZEN'                              # 而这个码在 _generate_fill_updates 里直接抛、不重试
```

模型没法保证「恰好把这一批 ID 全写到」。少一个就整轮报废。

**修法**：分两套口径。

| 来源 | 口径 |
|---|---|
| `args['nodes']`（调用方**显式**传的，如 `loop.py` 的 `fill_segment(node_ids=...)` 不传 nodes） | **strict**：必须完整，违约就 `SKELETON_FROZEN` |
| `_generate_fill_updates`（**模型自动**填的） | **宽松**：少给的下轮补，多给/编造的忽略，一个都对不上才报 `INVALID_FILL`（可重试） |

**② `fill_segment` 谎报完成数**

```python
return success(nodes=len(pending), node_ids=pending)   # 返回「请求的」
```
只填了 3 个也报 10 个 —— 上层会以为都完成了。

**修法**：返回 `updates`（**实际填上的**）。

**③ `loop.py` 的填充是一次性遍历，漏掉的永远补不上**

```python
for offset in range(0, len(pending), batch_size):   # 只走一遍，不回头
```
配合 ① 的宽容，少填的节点会一直停在 pending，而且没有任何机会补。

**修法**：外层加 `FILL_ROUNDS = 3` 轮补齐，每轮重新算 `pending`，空了就 break；
进度、checkpoint、publish 都用**实际状态**重算，不用累加。

### 验证

| 项 | 结果 |
|---|---|
| `tests.test_skeleton` 23 项 | **OK**（含 `test_fill_rejects_choices_and_node_changes` 的三种违约仍按 strict 拒） |
| 全量单测 81 项 | `failures=4, errors=6` —— 与改前一致，**无回归** |
| `_qa/_test_skeleton_e2e.py 140` | 全过，台词全填，validate_graph 通过 |

### 注意

`loop.py` 的 resume 分支读的是**检查点**（`checkpoints/ck-*.json`），不是 `graph.json`。
所以「5」虽然 `graph.json` 只有 2 节点，**骨架仍在 `ck-000025.json` 里**，
重新生成会走「从已冻结的骨架续写」，**跳过骨架生成**（省一次 60 秒的模型调用）。

## 16. 无参考图 + 无配音：只凭一句提示词生成（第 473 轮，主人要求）

### 原来的缺口

skill 里**完全没有「没有参考图怎么办」这条路径**（`grep 没有参考图|无参考` 零命中）。
所有美术文档都默认「有图可照着画」，可实际使用里用户很可能只填一行需求就开跑。

### 核心结论：一致性只能靠三根柱子

| 柱子 | 做法 | 崩了会怎样 |
|---|---|---|
| **一份外形锚点** | `look` 逐字复用，一个标点都不改 | 第 3 章换脸 |
| **一张基准图** | 每个角色先出「定妆照」，差分全拿它做 I2I | 立绘各有各的画风 |
| **一个固定种子** | 同角色同 seed | 同一表情每张都不同 |

有参考图时，一致性来自「照着那张图画」；没图时只能来自这三样。

### 落地：新增 `app/skills/art/08-no-reference.md`

| 节 | 内容 |
|---|---|
| 一、先造人 | **外形锚点五要素**（发型发色 / 眼睛 / 常服 / 体型身高 / 年龄气质）+ 禁用形容词（漂亮、可爱、唯美、精致…），每要素给「缺了会怎样」 |
| 二、定妆照 | 全身 / 正面 / 自然站姿 / 纯色底 / 平静表情；**先出 base 再出差分**，跳过会报 `BASE_ART_MISSING` |
| 三、背景 | 扫全部 `bg_prompt` 归并成 15~30 个地点；每个地点写**空间锚点五要素**，重点是「**记忆点物件**」（换时段时玩家靠它认出还是这里） |
| 四、没配音 | **不是跳过，是每句放静音**：`len(text)/4.5` 秒（与代码 `_duration` 完全一致）、24 kHz/16-bit/单声道、不许 `dur=0`、不许伪造语音 |
| 五、验收清单 | 10 条，含「`look` 五要素齐」「禁形容词」「有定妆照」「无 dur≤0」 |
| 六、常见崩坏 | 6 种现象 → 真正原因 → 修法 |

### 最上游的洞：`OUTLINE_SYSTEM` 根本没提 `look`

技能文档写得再好，**骨架阶段的模型读不到就是白写**。
`app/agents/outline.py` 的 `OUTLINE_SYSTEM` 原来只讲图的拓扑规则，对 `characters.look` **一个字没有**，
模型只会随手写「一个漂亮的女孩」—— 美术拿到这个必然画崩。

> 体型身高 + 年龄气质」这五样的名词和数字……禁止用漂亮、可爱这类形容词 ——
> 美术要照着这段逐字重画每一张立绘。用户没传参考图时，外形由你从需求里定；
> 一旦定了，后续任何地方都不许改写。

同时把 schema 里 `characters` 的 description 也写清了。

### 三处交叉引用（让 agent 真能读到）

- `art/SKILL.md`：细则清单加 `07-pose-diff.md`、`08-no-reference.md`

## 17. 关闭奇迹工坊时闪黑框（第 474 轮）

### 症状

关闭奇迹工坊窗口时，会弹出一个 cmd 黑框闪一下。

### 根因

`launcher/galapp.py` 的 `stop_children()`：

```python
subprocess.run(['taskkill', '/PID', str(proc.pid), '/T', '/F'],
               stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
```

**`taskkill` 是控制台程序。** 不指定 `CREATE_NO_WINDOW` 时，Windows 会给它**新建一个控制台窗口** ——
就是那个一闪而过的黑框。启动器本身是 GUI 进程（没有控制台），所以子进程必然新开一个。

### 修法

```python
_flags = getattr(subprocess, 'CREATE_NO_WINDOW', 0)
result = subprocess.run(['taskkill', '/PID', str(proc.pid), '/T', '/F'],
                        capture_output=True, text=True, creationflags=_flags)
if result.returncode != 0:
    detail = (result.stderr or result.stdout or '').strip()[:200]
    log('关闭[%s] taskkill 失败 rc=%s：%s' % (name, result.returncode, detail))
```

顺手修了同一条链上的第二个缺陷：**以前把 stdout/stderr 全丢掉，杀不掉也不留痕迹**。
「Access denied」这种失败如果静默，表现就是「界面关了、后端还活着」，下次启动复用僵尸进程，极难查。

`explorer /select,` 那处也补了 flags（它是 GUI 程序、本来不弹，统一规格）。
**`msedge` 那处不动** —— 那边注释明确记着踩过的坑（作业限制 / 句柄继承 / 白屏），且 Edge 是 GUI 程序不会弹窗。

### 实测（`_qa/_test_silent_close.py`）

真起子进程、真调 `stop_children()`，同时用 `EnumWindows` 数 `ConsoleWindowClass` 窗口：

| 检查 | 结果 |
|---|---|
| 起 2 个后台子进程 → 调 `stop_children()` | 115 次采样，**窗口峰值 0**（基线 0） |
| 子进程是否被杀掉 | **全部杀掉** |
| 失败留痕 | 沙箱权限不足时（`taskkill` 报 `Access denied`，**不带 flags 也一样**）日志确实记下了 |

> 对照组（taskkill 不带 flags）没抓到窗口，是因为 taskkill 执行太快、2ms 采样抓不到 ——
> 这一项只作参考，真正结论来自平台语义（`CREATE_NO_WINDOW` 不创建控制台）+ 主进程实测。

## 18. 章节切换与出口去向（第 475 轮，主人要求）

### 需求原话

> 章节切换节点也要安排上，有的节点是切坏结局，有的切好结局，有的单纯切下一章节

### 改法：给每个出口加「去向」

`SkeletonNode` 新增 `exit_kinds: list[str]`，和 `to` 一一对应：

| 取值 | 含义 |
|---|---|
| `chapter` | 进下一章 |
| `true` / `good` / `bad` / `alt` | 切对应类型的结局（与 `ENDING_KINDS` 对齐） |

**留空自动推断**（目标是 ending 就取它的 `end_kind`，否则 `chapter`），

`to_graph_stub` 把它写进 `choices[].kind`，契约 `app/contract.py::Choice` 同步加了
`kind: str | None`（可选，向后兼容）。

1. `exit_kinds` 数量必须等于出口数
2. `kind` 必须是 `EXIT_KINDS` 里的值
3. **声明必须和目标一致**：
   - 标 `chapter` → 目标不能是 `ending`
   - 标 `true/good/bad/alt` → 目标必须是 ending，且 `end_kind` 等于它

### 章节切换要有选择

`OUTLINE_SYSTEM` 现在明确要求：

> 章节之间的切换必须放一个 choice 节点，不要用 scene 直接跳到下一章 ——
> 玩家在切换点上要有选择，典型是「就此收手」（通向 bad 结局）和「继续追查」（进入下一章）。

校验层面这条**只记提示不阻塞**（写进 `meta.structure_warnings`）：
离线兜底图按节点序号切章，硬拦会把 `mock_skeleton` 打挂；

## 19. 「LLM 未返回合法 JSON」其实是输出被截断（第 476 轮）

### 症状

界面上报：

> LLM 未返回合法 JSON：{ "nodes": [{ "ref": "k029", "type": "scene", ...

**看起来像合法 JSON 的开头**，容易误判成「模型乱写格式」。

### 真相

项目日志里存着**完整原文**，尾巴是这样断的：

```
      "title": "站台风",
      "act": 1,
                              ← 后面本应有 "chapter": ...，没了
```

**JSON 写到一半就断了，压根没闭合。**

`app/providers/llm.py` 的 `call_json` 用 `text[:300]` 打印错误，**只显示开头**，
所以从界面上根本看不出「是截断」，只能看到「像 JSON」。

### 根因

骨架一次要 32 个节点，每个节点带 ref/type/title/act/chapter/to/labels/summary，
中文 token 消耗高 —— **`max_tokens=6144` 装不下**。

### 修法（三处）

| 位置 | 原来 | 现在 |
|---|---|---|
| `outline.py::OUTLINE_BATCH_SIZE` | 32 | **20**（一批写少点，更稳） |
| `outline.py` 骨架调用 | `max_tokens=6144` | **8192** |
| `fill.py` 填充调用 | `max_tokens=6144` | **8192**（一批 20 节点数行台词也吃紧） |

**顺手把报错改得能一眼分辨截断**：

```python
tail = text[-200:] if len(text) > 200 else ''
raise ProviderError('INVALID_JSON',
    f'LLM 未返回合法 JSON（共 {len(text)} 字符，若结尾是半截字段多半被 max_tokens 截断）：'
    f'开头 {text[:200]}' + (f' …… 结尾 {tail}' if tail else ''), ...)
```

以后再看这个错，**结尾和总长度**会直接告诉你是截断还是格式错。

### 验证

| 项 | 结果 |
|---|---|
| `_qa/_test_outline_model_path.py` | **全过**（64 节点现在切 4 批，每批 ≤ 20） |
| `_qa/_test_skeleton_e2e.py 140` | **140/140，0 断头** |
| 全量单测 81 项 | `failures=4, errors=6` —— 与基准一致，**无回归** |

### 我自己的失误（记下来提醒）

改 `fill.py` 时加了注释但没对齐缩进，`try:` 下面空了，直接
`IndentationError: expected an indented block after 'try' statement on line 106`，
整个生成任务在 `jobs.generate` 就挂了。
**改完之后必须跑一次 `ast.parse` 或单测**，不能只看「编辑成功」。

### 教训

> 看到「LLM 未返回合法 JSON」，**先去项目日志看尾巴**，不要只看界面那 300 字。
> 中文 JSON 一次写 30 个节点就是 6000+ token，批次和上限都要留余量。

## 20. 「骨架节点 ref 重复」——模型会把同一编号写两遍（第 477 轮）

### 现场

界面报 `骨架节点 ref 重复：k161`。项目日志里是连续三次：

```
正在生成整图骨架，目标 180 个节点
第 1 次骨架未通过校验：骨架节点 ref 重复：k081
第 2 次骨架未通过校验：骨架节点 ref 重复：k061
第 3 次骨架未通过校验：骨架节点 ref 重复：k161
error: 骨架节点 ref 重复：k161
```

**每次重复的编号都不一样** → 不是某一次手滑，是**模型在同批里把某个 ref 写了两个节点**。
批次越多（180 节点 / 9 批）越容易犯。

### 修法：去重，保留第一次出现

`_model_skeleton` 收齐所有批次后，先按 ref 去重再构造 `Skeleton`：

```python
seen_refs, unique_nodes, dropped = set(), [], 0
for item in nodes:
    ref = item.get('ref') if isinstance(item, dict) else None
    if isinstance(ref, str):
        if ref in seen_refs:
            dropped += 1
            continue
        seen_refs.add(ref)
    unique_nodes.append(item)
```

**为什么去重是安全的**：所有 `to` 引用仍然指向**第一个**那个节点，
图结构不会断；丢掉的只是重复副本（那份剧情本来也写重了）。

去重数量记进 `meta.structure_warnings`（不能另开字段 —— `meta` 是
`additionalProperties: False`，上次就是这么整挂的）。

同时 `OUTLINE_SYSTEM` 加了一条硬要求：

> ★ 每个 ref 在全图里**只能出现一次**：本批只写 refs 里列出的那些编号，
> 同一个编号不要写两个节点（写重了会被丢弃，那份剧情就白写了）。

### 验证（`_qa/_test_dup_ref.py`）

| 用例 | 结果 |
|---|---|
| 第一批里塞一个重复的 ref | 骨架成功产出、**无重复 ref**、保留第一次出现的、0 断头 |
| 去重被记进 `structure_warnings` | ✓ |
| 对照：重复放在**最后一批**（跨批边界） | 也能正确去重 |

另外 `_qa/_test_outline_model_path.py`、`tests.test_skeleton`、全量 81 项均无回归
（`failures=4, errors=6`，与基准一致）。

### 一句话

> 模型不是故意的，它是「写着写着忘了自己写过」。
> 对这种错，**去重比报错重试划算**——重试三次它还会再犯一次。
> 但要在提示词里明说，让它少丢东西。

## 21. 出口去向：从「硬校验」改成「以目标为准自动纠正」（第 478 轮）

### 现场（主人第二次跑同一个项目）

```
k120 第 2 个出口标成 bad，但 k180 的 end_kind 是 true
```

**这是我上一轮自己加的那道一致性校验在阻塞**：模型在出口上标了 `bad`，
但目标节点自己写的是 `end_kind=true`。

### 设计错误在哪

我把 `exit_kinds`（源节点上的**猜测**）和 `end_kind`（目标节点上的**声明**）
放在了同等地位，不一致就报错。但这两者根本不是一回事：

| 字段 | 谁写的 | 可信度 |
|---|---|---|
| `exit_kinds`（出口） | 模型顺手填的规划意图 | **低**——它记不清每个目标是什么 |
| `end_kind`（ending 节点） | 模型给结局定的类型 | **高**——节点自己是什么就是什么 |

**正确做法：单一真相源 —— 永远以目标节点为准。**

### 改法

**① `to_graph_stub`：最终 `kind` 一律由目标节点决定**

```python
kind = target_node.end_kind if target_node.type == 'ending' else 'chapter'
```

出口上的 `exit_kinds` 只当模型的规划意图，**不写进图数据**。

**② `validate_skeleton`：不一致时记 warning，不再 raise**

三种错都自动纠正并留痕：

- 标 `chapter` 但目标是 ending → 按目标的 `end_kind`
- 标某结局但目标不是 ending → 按 `chapter`
- 标 `bad` 但目标 `end_kind=true` → 按 `true`

### 验证（`_qa/_test_exit_kind_mismatch.py`）

| 用例 | 结果 |
|---|---|
| 出口指向 ending 却标「下一章」 | 纠正成目标 `end_kind` ✓，并记 warning |
| 出口指向 scene 却标「坏结局」 | 纠正成 `chapter` ✓ |
| 全图出口声明**全部故意写错** | 纠正后 **0 处不一致** |
| **180 节点 / 9 批，每个出口都标 bad**（主人真实规模） | **产出 180 节点、0 不一致、0 断头** |
| 对照：断头节点 | **仍然报错**（该拦的没松） |

其余：`tests.test_skeleton` 23 项 OK、全量 81 项 `failures=4, errors=6`（无回归）、
e2e 140 全过、模型路径测试全过、重复 ref 测试全过。

### 教训（写给以后的我）

1. **校验的硬度和它的"可信度"必须匹配**：
   高可信的数据（结构、断头、可达）该硬拦；
   低可信的（模型的猜测、标注、命名）该自动纠正。
2. **测试要覆盖"模型不听话"**，不能只测"代码逻辑对不对"。
   上一轮我测了「声明和目标一致」的情况，没测「声明乱写」——
   主人的真实输入恰恰是后者。
3. 主人说得对：**「测试好了再叫我」** ——
   这里的"测试好"包括**按真实规模、真实脏数据跑一遍**，不只是单元测试绿。

## 24. 「一屏十几二十个选项」根因定案（2026-11-10 晚）

主人截图：播放器一屏 12 个按钮，出现字面量「选项 C」「选项 D」，同一组选项重复三遍。
**不是模型乱写，是 `edges` 双真相 + 前端保存无去重。**

### 24.1 取证（项目 `p_04927612e8c44ec0b5519223a2a464e5`，128 节点）

| 指标 | 实测 |
|---|---|
| 节点类型 | scene 93 / choice 30 / ending 4 / start 1 |
| `edges` 总数 | **640**，唯一 `(from,port,to)` 只有 **114**，冗余 526（82%） |
| `choices` 长度分布 | `{2: 19 个, 4: 1 个, 26: 10 个}`，26 = 2 个真选项 × 13 遍 |
| `n1`（start）出边 | **27 条**（本该 1 条） |
| edge id 构成 | 后端 `e_nN_i` **52 条** + 前端 `e{数字}` **588 条** |

**`588 = 14 × 42`** ⇒ 前端每保存一次，就把「本章 42 条边」原样追加一遍，共存了 14 次。
这张图最初只有 52 条边。

### 24.2 四条根因（带代码位置）

1. **双真相**：`edges` 与 `nodes[].choices` 都在存连接，无强制投影。
   id 规则两边不一样：`graph.py:56` 是 `e_{nid}_{i}`，`ui/app.js:3932` 是 `e{i+1}`。
2. **前端合并无去重**：`ui/app.js:912`
   `links = links.filter(一端在章外).concat(d.links)`，全程没有按 `(from,port)` 去重。
3. **保存接口只跑 pydantic**：`app/mock_api.py:934` 只有 `Graph.model_validate(body)`，
   **没调 `validate_graph`** → 27 条出边 / 26 个选项原样落盘。
   而 `validate_graph` 的「edges 与 choices 不一致」（`graph.py:103`）、
   「分支须 2–4 个」（`tools.py:1457`）都装在没人走的路上。
4. **生成器形状是树**：`build_template()` 每分支长子树 ⇒ 叶子必然断头。

### 24.3 顺带查出的独立漏点

- **占位标签漏进播放器**：`graph-editor.js:836` 的 `['选项 A'..'选项 D']`、
  `app.js:1431` 的 `选项 A/B` 是画布占位，保存时没过滤 → 玩家看到「选项 C」。
- **`tools.py:1460` 的去重校验是错的**：`len({c['to'] for c in choices}) != len(choices)`
  会把合法的「气氛选项」（多选项指向同一节点）判非法。真实 galgame 里这是常态。

### 24.4 去重能不能救？（已实测：不能）

| 项目 | 去重后选项非法 | 去重后断头（非 ending 无出边） |
|---|---|---|
| hyd 128 节点 | 0 | **32** |
| p_ff87 96 节点 | 3 | **37** |
| 「5」88 节点 | 0 | **24** |

⇒ 去重只消「一屏按钮」，消不掉断头。**断头是生成阶段就没长出来的窟窿。**

### 24.5 产出

`docs/提示词-重做节点生成系统.md`（736 行 / 29 KB），交给 Astra 重写。
