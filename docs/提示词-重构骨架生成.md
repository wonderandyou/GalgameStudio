# 任务：重构 GalgameStudio「整图骨架生成」，让它稳定产出合法 DAG

## 0. 一句话说清问题

现在的骨架生成流程是：

```
让模型自由画一张图（分批） → 代码校验 → 不合格就带原因重试 → 3 次都失败就整轮报废
```

**模型几乎每次都会犯一种结构错误**，而这三种错误又互相独立、层出不穷：

| # | 实测错误（日志原文） | 模型为什么犯 |
|---|---|---|
| ① | `骨架节点 ref 重复：k161` | 它「写着写着忘了自己写过」 |
| ② | `骨架有环，k061 无法完成拓扑排序` | 两条支线互相回连 |
| ③ | `k156 是断头节点，非 ending 必须有出口` | 写到最后一个节点忘了给出路 |
| ④ | `k120 第 2 个出口标成 bad，但 k180 的 end_kind 是 true` | 出口上的标注是猜的 |
| ⑤ | `k056 的分支深度 3 超过上限 2` | 它不知道「嵌套」怎么数 |
| ⑥ | `骨架节点数 150 超出目标 100 的 ±10%` | 它控制不好数量 |

**每打一个补丁，下一个错误就冒出来。** 这条路的尽头是不存在的 ——
只要「结构」是模型自由生成的，就必须永远和它的不确定性搏斗。

## 2. 目标

**让「结构」由代码保证，模型只负责内容。**

具体要求：

1. **180 节点、9 批、任意模型输出**（包括上面 ①~⑥ 全叠上），
   **一次生成必须成功**，产出的图必须是合法 DAG。
2. 结构硬指标一条不许松：
   - 有且只有一个 `start`（且是第一个节点）
   - 所有节点从 `start` 可达
   - 无环（拓扑排序能排完）
   - 非 ending 节点必须有出口（**0 断头**）
   - 至少一个 `end_kind='true'` 的结局
   - `flavor` 分支的所有路线必须汇合到同一个节点
3. **模型仍然要有发挥空间**：剧情、标题、摘要、分支选项文案、角色设定都得是模型写的。
4. 不许改前端契约（`app/contract.py` 的 `Node` / `Choice` 字段结构，只能加可选字段）。

## 3. 推荐方案：**结构模板 + 模型填内容**

### 3.1 核心思想

```
[代码]  生成一张拓扑合法的大树骨架（DAG、有汇合、有结局）
   ↓   每个节点只留一个「槽位」：title / summary / 分支标签
[模型]  按章节读槽位，把剧情填进去（不碰结构）
   ↓
[代码]  合并 → 校验（此时几乎不可能失败，因为结构是代码造的）
```

**这条路的好处**：模型再怎么写错、写漏、写重，**都只影响内容，不影响结构**。
断头、环、不可达这些错误**从根上不可能出现**。

### 3.2 为什么不用「继续加校验」

- 校验越严 → 重试越多 → 烧时间烧钱
- 模型每次犯的错还不一样，补充性的补丁永远追不上
- 用户看到的是「失败了」，不是「模型不听话」

**校验只保留最后一道网**：`validate_skeleton` 仍然跑，但预期它**几乎不会失败**；
失败就说明代码有 bug，而不是「模型又乱来了」。

### 3.3 现有的可复用资产

- **`mock_skeleton()`**（`app/agents/outline.py`）已经是纯算法生成合法 DAG，
  每个菱形的两条腿都会汇合到一个「重新会面」节点。
  **把它当成模板生成器**，参数化（节点数 / 层数 / 分支数 / 结局数）。
- **`Skeleton` / `SkeletonNode` / `validate_skeleton` / `to_graph_stub`**
  （`app/engine/skeleton.py`）都可以直接复用，不用重写。
- **`fill_nodes()`**（`app/agents/fill.py`）已经负责「只填内容」，可以扩展成
  「按模板槽位批量出内容」。

## 4. 详细设计

### 4.1 第一步：代码生成拓扑模板

写一个新函数（建议放 `app/engine/template.py`，或作为 `outline.py` 的 `build_template`）：

```python
def build_template(*, target_nodes, depth, endings, key_branches, flavor_branches):
    """纯算法生成一张合法骨架的「空壳」，返回 SkeletonNode 列表。

    必须满足（由代码保证，不依赖模型）：
      · 唯一 start，排在第一个
      · 全部节点可达
      · 无环
      · 非 ending 都有出口（0 断头）
      · depth 限制：任意从 start 到某节点的路径上，最多 depth 个「还没汇合」的 choice
      · flavor 分支的所有出口最终汇合到同一个节点
      · 结局数 == endings，且至少一个 end_kind='true'
    """
```

**布局建议**（参考现有 `mock_skeleton`，但把「章节」显式化）：

```
start
  ├─ 第1章主线段落（scene…）…
  ├─ 章末 choice（key 分支）
  │    ├─ 腿A → 汇合点
  │    └─ 腿B → 汇合点
  ├─ …（按 key_branches / flavor_branches 数量循环）…
  └─ 最终分歧 choice
       ├─ ending(true)
       ├─ ending(good)
       ├─ ending(bad)
       └─ ending(alt)
```

**关键约束**：每个 `choice` 的**所有出口必须最终汇合到同一个 postdominator**
（除了通向 ending 的）。现有 `_branch_depth` 已经用 postdominator 算这个，
可以参考它的思路（`app/engine/skeleton.py::_branch_depth`）。

### 4.2 第二步：给每个槽位配「填内容」的请求

模板造好后，**不要**让模型碰 `type` / `to` / `ref`，只给它：

```json
{
  "requirement": "用户的原始需求",
  "logline": "（模型上一轮给的，用于保持前后一致）",
  "characters": [...],
  "slots": [
    {"ref": "k001", "kind": "start",   "hint": "开篇，要交代时间和地点"},
    {"ref": "k002", "kind": "scene",   "hint": "主线推进"},
    {"ref": "k010", "kind": "choice",  "hint": "玩家要在两条线索里选一条",
     "labels": ["核对来信", "听完口述"]},
    {"ref": "k050", "kind": "ending",  "end_kind": "bad",
     "hint": "坏结局：两人最终没说出口"}
  ]
}
```

**模型只需返回**：

```json
{
  "logline": "...",
  "characters": [...],
  "nodes": [
    {"ref": "k001", "title": "序幕", "summary": "雨夜里两人第一次正面对上那封信"},
    {"ref": "k002", "title": "旧照片", "summary": "..."}
  ]
}
```

**注意**：
- 返回里**没有** `type` / `to` / `labels` / `end_kind` —— 结构字段一律不允许模型给
- 如果模型多给了结构字段，**直接丢弃**，不要报错（这点很重要，见第 6 节）
- 模型的 `ref` 可能少给、多给、写重 —— **全部按「按 ref 填进模板」处理**，
  缺的槽位用兜底文案（`"{title}这一幕的台词正在准备"` 之类），多的丢掉

### 4.3 第三步：合并 + 校验

```python
def assemble(template, filled):
    """把模型填的内容按 ref 合进模板，结构字段一律以模板为准。"""
    by_ref = {item['ref']: item for item in filled}
    for node in template.nodes:
        content = by_ref.get(node.ref) or {}
        node.title = content.get('title') or node.title
        node.summary = content.get('summary') or node.summary
    return template
```

然后照常 `validate_skeleton(...)`。**它应该 100% 通过** ——
如果没过，说明模板生成有 bug，**不是模型的问题**。

### 4.4 分批策略

- 模板可能有 180 个槽位，**一次给模型太多它会漏**
- 建议**按章节分批**（每批 15~25 个槽位），每批带上一批的 `handoff`（前情提要）
- 批次失败只影响那一批的内容，**结构早已固定，不会整轮报废**
- 每批最多重试 2 次；仍失败就用兜底文案占位，继续下一批

## 6. 硬性纪律（这几条是踩出来的，别犯）

### 6.1 不许把「模型的可信度」和「结构的硬指标」放在同一条线上

| 类别 | 例子 | 该怎么做 |
|---|---|---|
| **硬指标**（代码能保证） | 断头、环、可达、唯一 start、结局存在 | 代码保证，校验兜底 |
| **模型的猜测**（低可信） | ref 重复、id 写错、出口标错、批次漏写 | **丢/纠正，不报错** |

### 6.2 报错信息必须能区分「截断」和「格式错」

`app/providers/llm.py::call_json` 已经改成带**总长度 + 结尾 200 字**，
保留这个做法。截断的典型表现是「JSON 写到一半突然没了」。

### 6.3 token 上限要留余量

中文 JSON 一次写 20 个节点大约 4000~6000 token。
当前设置：`OUTLINE_BATCH_SIZE = 20`、`max_tokens=8192`（`outline.py`），
`fill.py` 也是 8192。**别往回调小**。

### 6.4 改完必须真跑

- 单测：`python -m unittest discover -s tests -p "test_*.py"`（当前基线 `failures=4, errors=6`，别更差）
- 端到端：`_qa\_test_skeleton_e2e.py 140`（必须 0 断头、全部 done）
- **模型路径**：`_qa\_test_outline_model_path.py`（用假 provider 模拟模型行为）
- **脏数据**：`_qa\_test_structure_repair.py`（五种病全叠上，156 节点）
- 改完 `ast.parse` 或跑单测，**别只看到"编辑成功"就交**（我加过注释忘改缩进，
  直接 `IndentationError`，整轮任务在 `jobs.generate` 就挂了）
